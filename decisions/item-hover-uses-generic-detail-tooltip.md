# Item hover uses the generic `<detail-tooltip>`; every item renders through one `<item-chip>` component

`<detail-tooltip>` (`public/components/detail-tooltip.js`) is a domain-agnostic `{ name, description?, stats? }` renderer — it has no knowledge of what kind of entity it's showing. That part hasn't changed.

What has: every place an *item* renders as a hoverable chip (a quest reward, an npc drop, a recipe ingredient, an item mentioned in the Leveling Guide's hand-authored prose) now renders through one shared component, `<item-chip>` (`public/components/item-chip.js`), instead of each card owning its own copy of the badge markup/CSS and its own `itemStats(item)` + hover-wiring. An earlier pass had that duplicated four ways — `quest-shared.js`'s `itemChip()`/`.item-badge`, `zone-dossier.js`'s `.npc-drop-badge`, `tradeskill-shared.js`'s `ingredientChip()`, and `leveling-guide.html`'s own `.loot-badge` — each with near-identical CSS and its own `mouseover`/`mouseout`/`click` delegation. That drift is exactly the failure mode to avoid: an item should look and behave identically everywhere, and there should be exactly one place that decides what "an item" looks like.

`<item-chip>` owns the whole thing: the gem-dot + name markup, the wiki link, `itemStats()` (item fields → `<detail-tooltip>`'s generic stat-chip contract), and the hover/tap wiring itself (each instance wires its own listeners in `connectedCallback`, no parent-level event delegation needed). A card that already has the full item object calls `chip.setData(item)` directly; a card that builds its chips as one HTML string emits `itemChipTag(item)` and then calls `hydrateItemChips(root, findItem)` once that markup is in the DOM — the same "markup first, data after" split `leveling-guide.html`'s hand-authored prose already needed (its chips exist in static HTML before the matching items are ever fetched).

This is scoped to items specifically — `zone-card.js`'s `spellStats(spell)` (spell fields → stat chips) is a different domain with only one real hover site, so it stays as its own local function next to the data that produces it. The rule isn't "every entity type must funnel through one shared component" — it's "don't let the *same* entity type's rendering drift across files." A genuinely new entity type wanting hover detail should ask first whether it already renders in more than one place; if so, it gets its own shared chip component the same way items did, not a per-card copy.
