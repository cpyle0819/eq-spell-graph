# `npc --drops--> item`, and `item --located_in--> zone`

Until migration 267, an `item` node's only provenance edge was `quest --rewards--> item` — there was no way to say a named mob drops a piece of gear directly, outside a quest. Two additions:

- `npc --drops--> item`: added only when eqlwiki.com's own zone page states the specific NPC that drops the item (e.g. Shiny Brass Shield from Crushbone's Orc Trainer). Not backfilled onto items whose page only lists them as "zone drops" with no named source.
- `item --located_in--> zone`: reuses the existing edge type for a new source-node type, the same way `quest --located_in--> zone` already reuses it alongside `npc --located_in--> zone` (see [edge-semantics.md](edge-semantics.md)). Every item gets this even when it also has a `drops` edge, so "what's in this zone" queries don't need to join through an npc.

## `method`/`mobs` (issue #55): distinguishing *how* an item is obtained at a zone

Both edges above only ever recorded *that* an item comes from a zone/npc, not *how* — fine for gear (usually just one drop source), not enough once tradeskill ingredients needed their own "Foraged In"/"Fished From"/"Dropped By" sections (`ingredient-card.js`) distinct from "Sold By". Rather than three new edge types, `item --located_in--> zone` grows a `method: "drop" | "forage" | "fish"` attribute (`EdgeData` in `src/graph.ts`) — same "grow an attribute when real data needs it" call as `quantity`/`randomGroup`/`transport`. `method` is required whenever the edge's source is an item; it's meaningless (and unset) for the npc/quest-sourced `located_in` edges this same edge type already covers.

`drop`-method edges also carry an optional `mobs: string[]` — the specific creature name(s) eqlwiki's own item page lists under that zone heading (e.g. Bat Wing at Butcherblock Mountains: `["a bat"]`). This does **not** create new `npc` nodes for those mobs — trash-tier drop sources ("a bat," "a large rat") aren't modeled as real `npc` nodes anywhere in this graph (that's a much bigger bestiary undertaking, out of scope here), so `mobs` stays plain text on the edge rather than a real node reference, same "not every real-world entity needs its own node" reasoning as `quest.classes`.

**Sourcing**: eqlwiki's own `Itempage` template has real structured fields for this — `|dropsfrom = ` (zone headers, each followed by `* [[mob]]` bullets) and `|foraged = ` (a bare zone list, sometimes literally `Various` or free prose like "This item can be foraged in most zones" instead of a real zone). Fishing has **no structured field at all** — it only ever shows up as prose in `|notes = ` ("Obtained by fishing in [[Zone]]."), so a fish ingredient with no zone-naming prose (several of Baking's raw fish, e.g. Boar Carp, Highland Pike) gets no Fished From section at all rather than an invented one — same "absence is the real fact" precedent as `tradeskill-recipe-node-schema.md`'s un-sourced ingredients. Migration 370 batch-fetched all 208 of Brewing+Baking's `uses` ingredients directly from the wiki (not reused from the free-text `source` field already on many of these items, since that field is a lossy paraphrase written during earlier migrations, not itself independently wiki-verified at this granularity — tenet 2, accuracy over completeness, is what settled reusing-vs-reverifying here) and only added edges for zones that already exist as `zone` nodes in this graph — a handful of wiki zones aren't catalogued here yet (Erud's Crossing, Siren's Grotto, Tower of Frozen Shadow, Velketor's Labyrinth, Mines of Nurga) and are skipped rather than guessed at, same precedent as `tradeskill-recipe-node-schema.md`'s vendor skip list. Ambiguous unqualified wiki zone names ("Commonlands," "Kaladim" with no East/West or North/South) are skipped for the same reason. 3 of the 208 items have no findable wiki page at all under their graph label (Gray Ice, Human (Chunk of) Meat, Pondfish Spines) and keep only their existing free-text `source`, unbackfilled.
