# Wiki links: per-entity page vs. shared-page link, by node type

Issue #14 asked for eqlwiki.com links on cards/nodes throughout the app. Not every node type has its own page, so the link target depends on type:

- **Spells, abilities**: each has its own dedicated eqlwiki.com page titled exactly like the entry (`scripts/scrape-spell-details.ts` already fetches 1,059/1,064 spells this way; abilities live on their own "Skill X" pages, per decisions/abilities-tab-class-defining-actions.md). `spell-card`/`ability-card` link straight to `wikiUrl(entry.label)`.
- **Stances, invocations**: all 18 live on one shared "Stances & Invocations" page (decisions/stance-invocation-nodes-single-page-scrape.md) — `stance-card` links every entry to that one page, not a fabricated per-entity URL.
- **AAs**: all live on one shared "Alternate Advancement" page (decisions/aa-nodes-single-page-scrape-with-category.md) — `aa-card` links every entry to that one page, same reasoning.
- **Zones**: each has its own page, but the zone's graph `label` doesn't always match the page title 1:1 (decisions/zone-naming-mismatches.md — e.g. "East Cabilis" → "Cabilis"). Migration 023 adds a `wiki_title` field to every zone node (sourced from `data/zone-lore.json`'s already-resolved titles, the same resolution migration 022 used for `lore`), and `getZoneVendorInfo`/`rankZones` (src/graph.ts) both expose it as `wikiTitle` so zone-card/route-card link to the *actual* resolved page instead of guessing from `label`.
- **Quests, quest groups**: same `wiki_title` → `wikiTitle` field/convention as zones, added by migration 030 for the real (non-test) quests only. Several real quests here share one page with no page of their own — all 7 Armor of Ro sub-quests point at the same "Armor of Ro Quests" page, the same shared-page pattern as stances/invocations/AAs — and the fictional migration-026 test quest simply has no `wiki_title` at all, so `quest-card`/`quest-group-card` render no link rather than guess a likely-404 URL from the label. A quest group's member rows don't each repeat the link — it renders once, on the group's own card, since a member no longer has its own top-level card once it's part of a group (decisions/quest-group-card-ui.md).
- **Classes**: each has its own page (`eqlwiki.com/Warrior`, etc.), but classes have no card/node of their own anywhere in the UI — only a filter dimension. The link lives next to the one UI element where a *single* class is unambiguously in focus: Spell Finder's Primary Class `<select>` (always exactly one value or "any") and Class Browser's Classes tag-input, but only when it holds exactly one chip. Not added to every tag chip — would clutter a multi-select filter that's frequently in a "browsing several classes at once" or "no classes" state.

Shared helper: `public/components/card-base.js` exports `wikiUrl(pageTitle)` (title → URL, spaces → underscores → percent-encoded, the same convention validated at scale by the spell/zone scrapers) and `wikiLink(pageTitle)` (the actual `<a class="wiki-link">` markup) plus a `WIKI_LINK_CSS` string spliced into any shadow-DOM stylesheet that isn't already on `BASE_SHEET` (zone-card, route-card). `public/theme.css` has a light-DOM sibling `.wiki-link` rule for the two sidebar class links (plain page markup, not inside a shadow root). All wiki links are `target="_blank" rel="noopener"`, styled as a quiet dotted-underline-on-hover text link (matching `leveling-guide.html`'s existing `.ledger-item a` precedent) — metadata, not a card's primary action.
