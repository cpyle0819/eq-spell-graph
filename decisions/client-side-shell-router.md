# Client-side shell router: app-header/app-footer persist across navigation

`public/router.js` is the single script every page loads (`<script type="module" src="router.js">`), replacing each page's own `<script src="components.js">` + `<script type="module" src="app.js">` (etc.) pair. It intercepts same-origin clicks on links to this app's own five pages, fetches the target page's HTML, and swaps in only the page-specific `<style id="page-style">`, `<title>`, `<app-header>`'s attributes/slotted `<nav-links>` content, and everything in `<body>` that isn't `<app-header>`/`<app-footer>`/`<script>` — leaving the header and footer as the same live DOM nodes across the navigation instead of the browser tearing down and re-creating them on every click (issue #25: FOUC + shared chrome reloading on every navigation). Falls back to a real `location.href` navigation for anything it can't handle itself (cross-origin links, `target="_blank"`, a failed fetch) — it never silently swallows a click it can't complete.

**Page scripts export `init()`, they don't self-invoke.** `app.js`/`route.js`/`class-browser.js` used to end with a bare `init();` call that fired once when the module's top-level code ran. ES modules execute their top level exactly once per specifier (cached by URL) for the life of the document — since the router keeps the document alive across soft navigations instead of doing a real reload, a second visit to an already-imported page's module would never re-run that top-level call, and its content would never (re-)render. The router calls the exported `init()` itself after every swap, hard load or soft, via a small `PAGE_SCRIPTS` registry keyed by filename (`pageKey()` also maps `"/"` to `"index.html"`, mirroring `src/server.ts`'s own static-file rewrite — miss this and a root visit's `location.pathname` of `"/"` matches nothing, and `app.js`'s first-time-visitor redirect silently never runs).

**`components.js` is now a real ES module** (`export function getOwnedSpells() {...}`, etc.) instead of a classic script relying on `window` globals — a page arriving first at `home.html` or `leveling-guide.html` (neither of which used to load `components.js` at all) needs those functions available the moment it soft-navigates to `index.html`/`class-browser.html`, so they're `import`ed directly by whichever module actually calls them (`app.js`, `class-browser.js`, `components/spell-card.js`) rather than assumed to already be on `window`.

**Anchor detection uses `e.composedPath()`, not `e.target`.** Every link this router needs to catch — `nav-links`' buttons, `app-header`'s "Norraph" title, `spell-card`'s "Find in Spell Finder" link — renders inside a shadow root (`macro-button.js`, `app-header.js`, `spell-card.js`), and a document-level listener sees `e.target` retargeted to the shadow host, same quirk documented in `decisions/real-web-components-shadow-dom.md`. `composedPath()` exposes the real internal `<a>` regardless of listener position, since every shadow root in this app is `{mode: "open"}`.

**`document.startViewTransition(callback)`'s callback is not guaranteed to run synchronously just because the outer call returned** — confirmed empirically (Chromium 149): calling it and immediately proceeding left the DOM unswapped and the `init()` dispatch running against stale content. The transition object's `updateCallbackDone` promise is what actually resolves once the callback has run; the router `await`s that (when the API exists at all — it's a feature-detected, Chromium-only progressive enhancement, plain synchronous swap otherwise) before calling the page's `init()`.

**FOUC fix (`theme.css`): `*:not(:defined) { visibility: hidden }`.** Since virtually every visible element in this app is a custom element (see `decisions/real-web-components-shadow-dom.md`), the flash was custom elements rendering as blank, unstyled boxes holding their raw slotted text before `public/components/index.js` finished registering them. `:defined` matches all built-in elements unconditionally and only starts matching a given custom element once `customElements.define()` has run for its tag, so this hides exactly the not-yet-upgraded ones, with no per-tag list to maintain as components are added.
