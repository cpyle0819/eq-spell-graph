# Classes page's Quests category: "no selection" ≠ "everyone"

Quests surface as a new category on the Classes page (`class-browser.js`), alongside Spells/Abilities/Stances/Invocations/AAs — same tab mechanism, same `<quest-card>`/`<quest-group-card>` rendering as the standalone Quests tab (`buildQuestResultEntries()`, moved to `public/components/quest-shared.js` so both pages share it).

**Deliberate exception to `decisions/no-classes-selected-means-all-classes.md`.** Every other category on this page treats an empty class selection as "show everything" — that convention holds because those categories are either class-neutral by nature or their real "for anyone" entries are exactly what a browsing-with-no-filter visitor wants to see. Quests are different: with no class picked, the Quests category shows every quest tied to *some specific class*, not literally every quest — a classless "Any Class" quest (e.g. Journeyman's Boots) doesn't fit "browsing by class" the way it fits the standalone Quests tab's general-purpose framing. Picking one or more classes narrows to the union of just those classes, the same rule as everywhere else on this page.

This makes the Quests category's class-narrowing genuinely different from `getQuests()`'s own default (empty `classNames` = no filtering at all, per `decisions/quest-reward-modeling.md`) — so `class-browser.js` doesn't send a `class=` param to `/api/quests`/`/api/quest-groups` at all. It fetches both endpoints once, unfiltered, at page load (`init()`), and does 100% of the class-narrowing itself in `questsForClassBrowser()`, re-run on every `render()`. This is also why quests/quest groups aren't part of `fetchAbilities()`'s per-class-selection-change fetch cycle the other categories use — the full unfiltered set never changes based on class selection, only this page's own client-side filter over it does.
