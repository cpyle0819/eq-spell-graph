# Spell icons: real client art, a deliberate exception to the derived-facts-only policy

Every other local-client extraction in this repo (`scripts/extract-spell-lines.ts`, `scripts/scrape-spell-details.ts`) outputs only small derived facts — numbers, groupings — and explicitly never copies Daybreak's actual proprietary asset files into the repo (see `decisions/spell-lines-from-local-client.md`: "never the raw `spells_us.txt` itself... copying it wholesale into this repo is a different act than extracting a handful of already-public wiki facts"). Real per-spell icon art *is* the copyrighted asset, not a fact derived from it — committing it (`public/icons/spell-icons.png`, one packed sheet) is a knowing, deliberate departure from that policy for this one feature, made after surfacing the conflict explicitly (issue #21) rather than an accidental one. Revisit if this ever becomes a problem (e.g. a takedown request) — the CSS fallback (see below) means removing the images later degrades gracefully rather than breaking anything.

## Two wrong approaches before this one (issue #21 follow-up)

The repo owner reported the first shipped version's icons were wrong and asked to check them against eqlwiki.com. Two guesses failed before landing on the current approach — recorded here because both looked individually plausible (each passed its own spot-checks) and the failure mode is a useful cautionary example for reading too much into thematically-plausible-looking results without real ground truth:

1. **Guessed field 87** of `spells_us.txt`'s 173 `^`-delimited fields as the icon id, based on convergent clustering (every fire-named spell sharing one value, every ice-named spell sharing another) and several thematically-apt spot checks (Mesmerize → an eye, Fear → a clawing hand). Checked directly against eqlwiki.com's own `Spellicon_<id>.png` filenames (`curl <page> | grep -o 'Spellicon_[^."]*\.png'` — raw HTML, not an AI-summarized fetch, after a summary once misreported a filename outright) and it was simply wrong: Minor Healing's real icon is 99, not field 87's 42.
2. **Guessed field 75** instead — this one *did* match the wiki's numeric filename exactly, 8/8 spot checks (Flash of Light=23, Minor Healing=99, Cure Poison=42, Word of Healing=208, Light Healing=99, Charm=26, Invisibility=18, Mesmerize=35). The id was right, but the local `Spells<NN>.tga` sprite-sheet crop still rendered the wrong picture — downloading the wiki's actual reference image for icon 99 and brute-force pixel-searching all 63 local sheets for an exact match found it at sheet 1, position (0, 0), while icon 23 (a *smaller* number) sits three rows into the *same* sheet. There's no arithmetic relationship between an icon id and its position in the local sheets recoverable from anything this repo has access to — that packing lives in a lookup table inside the compiled client.

## What's actually shipped

`scripts/extract-spell-icons.ts` fetches each spell's own eqlwiki.com page directly (same URL convention as `public/components/card-base.js`'s `wikiUrl()`) and reads its `Spellicon_<key>.png` reference straight from the raw HTML — the wiki already hosts the correctly-cropped image per spell, so this sidesteps needing to know the local sheets' real layout at all. `<key>` is usually numeric but sometimes a single letter (e.g. "K") for spells — mostly buffs — the wiki itself apparently couldn't pin a confident number to either; both are downloaded and used as-is, since matching what eqlwiki.com displays is the actual goal, not a specific encoding. Outputs `data/spell-icons.json` (graph spell id → icon key, the derived fact) and one PNG per **distinct** key to `public/icons/` (1,059/1,064 spells matched, but only 118 distinct icons — heavily reused, same spirit as the spell-line grouping field's low-cardinality result).

`scripts/build-icon-sheet.ts` then packs those 118 individual PNGs into one combined sheet (`public/icons/spell-icons.png`, an 11x11 grid of 40x40 cells) plus `public/components/icon-sheet-manifest.js` (a plain JS module exporting each key's `{x, y}` pixel offset), and deletes the individual files — one small image and one small manifest ship instead of ~120 separate files.

## Schema and rendering

Migration 024 adds a plain top-level `icon` (string) field directly to matched spell nodes — `NodeData`'s open index signature (`[key: string]: unknown`) means no `src/graph.ts`/`src/api.ts` changes were needed for it to flow through `/api/spells` automatically, same as `mana`/`skill`/etc.

`public/components/spell-card.js` renders a `<span class="spell-icon">` with `background-image: url(icons/spell-icons.png)` and a per-instance inline `background-position` looked up from `ICON_SHEET_MANIFEST[spell.icon]`, falling back to the pre-existing decorative CSS gem (`zone-card.js`'s `.spell-chip::before` radial-gradient square, duplicated here as `.spell-icon-fallback`) when a spell has no icon key or the sheet doesn't (yet) contain it. Scoped to the Class Browser's spell cards per issue #21 — the Spell Finder's `zone-card` spell rows keep their existing plain `.spell-chip` treatment, not touched by this change.

Regenerating: re-run `scripts/extract-spell-icons.ts` then `scripts/build-icon-sheet.ts` (in that order — the second consumes the first's output) and `migrations/024-add-spell-icons.ts` if the spell roster or the wiki's own icons ever change.
