# Tradeskills: `recipe`/`container` node types, `uses`/`produces`/`crafted_in` edges

Issue #32 asked for tradeskill support (recipe lookup, ingredient lookup, per-trade leveling guides), starting with Brewing as the first modeled trade. No new "tradeskill" node — `tradeskill` is a plain string field on `recipe` (e.g. `"Brewing"`), the same "no node type for a fact that's just a string" call as `spell.class_levels`' `class` field or `quest.classes`. The Tradeskills page's own select box is populated from the distinct `tradeskill` values across `recipe` nodes, not a separate lookup table.

`recipe` node shape:

```ts
{
  id: "recipe:short-beer",
  label: "Short Beer",
  type: "recipe",
  tradeskill: "Brewing",
  trivial: 31,   // skill level at which this recipe stops reliably granting skill-ups
}
```

## Two different things eqlwiki calls a "container" — only one is a `container` node

The wiki's own Brewing recipe table has a "Container" column (Bottle/Cask/Shotglass/none) that reads as tradeskill-container terminology but is actually just another **consumed ingredient** — a recipe that fails still returns it, but a successful one uses it up the same as any other listed ingredient. This stays modeled exactly as any other ingredient: a `recipe --uses--> item` edge, no special casing.

The wiki also has a real, separate concept it groups under its own "Tradeskill Containers" category (Brew Barrel, Forge, Kiln, Pottery Wheel, Loom, Sewing Kit, Fletching Kit, Oven, Jeweler's Kit, Tackle Box, Medicine Bag, and several tomes/lexicons for Scribing) — the **stationary crafting station** a recipe is made *in*, never consumed, and normally the same one for every recipe in a given trade. eqlwiki's own Brew Barrel page: "A brew barrel is a stationary object with which players can interact in order to attempt a Brewing recipe. They are available in many locations around Norrath." And Skill Brewing's own basics section: "All combines are made in a brew barrel which can be found in most towns." *This* is what gets the new node type and edge:

- New node type: `container` (e.g. `container:brew-barrel`, label "Brew Barrel"). Brewing's own Brew Barrel is a pure world-fixture — not held in inventory, not sold by vendors, not consumed by anything — so migration 356 gave it none of `item`'s fields and no `sells`/`drops`/`located_in` edges.
- New edge type: `recipe --crafted_in--> container`, one per recipe (real per-recipe granularity even though every currently-modeled Brewing recipe points at the same Brew Barrel node — other trades' own container pages suggest a recipe-to-container relationship isn't always 1:1 per trade, e.g. Baking's Oven vs. Mixing Bowl vs. Spit). Deliberately not `requires` — that edge type already means "quest prerequisite chain" (decisions/quest-prerequisite-requires-edge.md), a real ordered dependency between two same-type nodes, not "the vessel this is made in."

**Update (Baking, issue #47): not every wiki "Tradeskill Container" is a Brew-Barrel-style world fixture.** Baking's own Oven matches Brew Barrel exactly (eqlwiki: "a stationary object with which the player may interact... available in major cities," no `soldby` table, no weight/capacity stat block). But Mixing Bowl and Spit — both filed under the same eqlwiki "Tradeskill Containers" category — are genuinely portable, vendor-purchased inventory items with a real weight/Capacity/Size-Capacity stat block, same shape as any other carryable item. They're still `container`-type nodes (they're what recipes' `crafted_in` edges point at, same functional role as Oven), but the earlier "none of item's fields, no sells edges" blanket claim only holds for the world-fixture kind. A `container` node gets `weight`/`source` (and `capacity`/`containerSize` per `item-node-schema.md`'s existing tradeskill-container fields) and `sells` edges whenever its own eqlwiki page actually shows them — Oven still gets none of that, Mixing Bowl and Spit do.

Ingredients and the crafted result are still edges, not fields — same "real entities get edges, not fields" reasoning as `quest --rewards--> item` (decisions/quest-reward-modeling.md):

- `recipe --uses--> item`: one edge per distinct ingredient, including the wiki's "Container" column vessel (Bottle/Cask/Shotglass — see above, this is not the same thing as a `container` node). `quantity` is an optional edge attribute (absent = 1), same "grows an attribute when real data needs it" precedent as `connects_to`'s `transport` and `rewards`' `randomGroup`.
- `recipe --produces--> item`: the crafted result. Also carries an optional `quantity` attribute for a >1 yield (absent = 1). This is an ordinary `item` node like any other real item — nothing stops it from also being a later recipe's ingredient (Short Beer and Gnomish Spirits are both mid-chain products and ingredients further up Brewing's own leveling path), the same way a quest reward item can also be a drop. **It renders through the same `<item-chip>` component as any other item in the UI** (public/components/item-chip.js, decisions/item-hover-uses-generic-detail-tooltip.md) — an earlier pass gave it a distinct green "reward" color, which read as a second kind of entity when it's really just an item like the rest; the only thing that should visually distinguish it is the → it follows in the recipe formula, not its color.

**Vendors selling tradeskill supplies reuse the existing `npc --sells--> item` edge** (decisions/edge-semantics.md), not a new edge type — `sellCategoryLabel()` in `src/graph.ts` already fell back to a generic plural label for any non-spell sell target before this, anticipating exactly this case. No `recipe`-to-`npc` edge at all: "where can I buy what I need" is answered by walking `recipe --uses--> item` to the ingredient set, then `item <--sells-- npc` for who sells them, not a direct link. Containers (the crafting-station kind) get no vendor edges at all — they're found in the world, not purchased.

## Success-chance thresholds are computed, not stored

`trivial` is the only skill-level fact sourced from eqlwiki itself. A player's actual success odds below that are a general tradeskill-mechanics formula (not Brewing-specific, not eqlwiki-sourced — supplied directly by the project owner, carried over from classic EQ's own well-known formula), so it's computed from `trivial` at read time (`recipeSuccessThresholds()` in `src/graph.ts`) rather than hand-entered per recipe in a migration — the same "don't store what's derivable" call as not giving `container` its own redundant `tradeskill` field (it's already derivable by walking `crafted_in` back to any recipe that points at it):

```
25% success: max(0, ceil(0.75 × trivial − 26.5))
50% success: max(0, ceil(0.75 × trivial − 1.5))
75% success: max(0, ceil(0.75 × trivial + 23.5))
95% success: trivial itself (capped there, not a fifth linear formula)
```

**Sourcing bar, same as `item-node-schema.md`'s**: Brewing's recipes came from eqlwiki.com's `Skill Brewing` page's raw wikitext (`action=query&prop=revisions`, not `WebFetch`'s summarizer — exact ingredient/trivial/container/yield data, no lossy paraphrase, fetched in batched multi-title queries for the ingredient items' own weight/size/vendor data too); the Brew Barrel container fact came the same way from its own page. Migration 355 modeled only the wiki's own "Antonica Biased Brewers" 11-recipe leveling path (triv 21 through 248) as a first pass; migration 358 later added the full remaining ~67 recipes from that same page's "Recipe List" table (78 total), so Recipes/Ingredients browsing covers the whole trade, not just the leveling spine. `recipe.levelingGuide` (migration 359) flags exactly those original 11 — the Leveling Guide UI filters on this field rather than "every recipe of the tradeskill," so it stays that same hand-picked path regardless of how much broader recipe-book coverage grows around it. Ingredients with no `soldby` table at all (Rat Ears, Vegetables, Berries, Fruit, and others — loot/forage only per the wiki) get no `sells` edge; that absence is itself the real fact, not a gap to fill in later. A vendor is only added when its own zone already exists as a `zone` node in this graph — a handful of wiki-listed zones (Kelethin, Erud's Crossing, Highpass Keep) aren't catalogued here yet and are skipped rather than guessed at; two zone names eqlwiki's vendor tables use for the same real place as this graph's own zone nodes (Eastern/Western "Plains of Karana" vs Eastern/Western Karana, "Neriak Third Gate" vs Neriak 3rd Gate) are resolved via a small alias map in migration 358, not treated as new zones.

## Recipe variants: same output item, different ingredient combos

Baking (issue #47) surfaced something Brewing never had: multiple distinct ingredient combos that produce the *same* output item — a classic-era combo and a Velious-era combo of the same food (e.g. Beer Braised Mammoth: Short Beer in one, Othmir Algae Ale + Algae Spices in the other), or the wiki's own explicit "**OR**" alternate ingredient lists (Frost Giant Steak, Storm Giant Steaks, Yakman Steak). Each combo is a real, independently craftable recipe — collapsing them into one node would silently drop whichever combo didn't get picked.

Each combo stays its own `recipe` node (same shape as any other recipe, including its own `produces` edge to the shared output item). A new edge links them as a family:

```
recipe --variant_of--> recipe
```

One recipe per family is the **anchor** (whichever combo a migration happens to add first — the choice has no semantic weight, it's just bookkeeping so the edge has somewhere to point); every sibling combo gets a `variant_of` edge pointing at it. This is a distinct edge from `produces` (which already, incidentally, links same-output recipes too) because relying on "shared `produces` target" alone would mean the read layer has to scan every recipe in a tradeskill and group by target on every request — an explicit edge makes a variant family a single edge-walk instead.

**Which variant is "primary" is computed at read time, not stored.** `getRecipes()` (`src/graph.ts`) groups each family (anchor + its `variant_of` siblings), scores every member by how many of its `uses` ingredients have at least one `sells` edge from any vendor, and surfaces the highest-scoring combo as the card's main formula — same "don't store what's derivable" reasoning as `trivial`'s success-threshold math above. This can flip which combo shows as primary if vendor data changes later (e.g. a new vendor batch makes the Velious combo's ingredients sourceable where before only the classic combo's were) without needing a migration to re-flag anything. The rest of the family ships on `RecipeSummary` as `variants: RecipeSummary[]` and renders in `recipe-card.js` as an expandable list (same `<details>`/`<summary>` pattern `quest-group-card.js` uses for its own member roster), not a second badge-cluttered card.

The ~10 near-duplicate "Fillets" combos on Baking's own page (Fish/Carp/Chub/Pike/Salmon/Trout fillet, differing only by which fished raw fish replaces Fresh Fish) are modeled the same way: each is its own recipe+item pair (a Carp Fillet is a different real item from a Fish Fillet), not a variant family of each other — "variant" means *same output item*, not "same category of food."

## `produces` can target a `container` node, not just `item`

Blacksmithing (issue #48) surfaced Pot and Smoker as genuinely player-crafted via Blacksmithing itself (Pot: Metal Bits + Pot Mold + Standing Legs Mold + Water Flask, trivial 122; Smoker: Metal Bits + Skewers + Smoker Base Mold + Smoker Support Mold + Water Flask, trivial 50) — but both nodes already existed as plain `container` nodes from Baking, referenced only via other recipes' `crafted_in` edges. No prior recipe had ever pointed a `produces` edge at a `container`.

This isn't a new edge type or a schema violation: the Mixing Bowl/Spit update above already established that a `container` node can carry `item`-like fields (weight, `source`, `sells` edges) whenever the wiki itself shows a portable, vendor-purchased container rather than a world fixture — Pot (WT 0.3) and Smoker (WT 0.4) both fit that same portable-container shape. `recipe --produces--> container` is simply the natural extension: the produced entity is still a real, already-modeled node: nothing about `produces` ever assumed its target had to be `type: "item"` specifically. Both Pot and Smoker are also craftable via Pottery on the same eqlwiki pages (different ingredients/trivials) — not modeled, since Pottery isn't in this graph yet.

## Pottery (issue #51): a genuine two-stage combine needs no schema change

Pottery is the first tradeskill modeled where a single finished item requires two distinct combines at two distinct stations: eqlwiki's own Basics section says it outright — "Pottery is produced in two stages. In the first stage you combine the appropriate sketch and a flask of water with clay and other materials on a pottery wheel. You then take the unfired result and combine it with firing sheets in the kiln to make a finished product." This needed no new edge type or node shape: it's just two chained `recipe` nodes (Wheel produces an "Unfired X" item, Kiln consumes that exact item and produces the finished good), the same chained-recipe shape Blacksmithing's own ore chain (Small Piece of Ore → Small Brick of Ore → Sheet Metal) already used — each recipe still has exactly one `crafted_in` edge, there just happen to be two recipes and two stations (`container:pottery-wheel`, `container:kiln`) per finished item instead of one. The "Unfired X" intermediate is an ordinary `item` node, nothing special — it just also happens to be another recipe's sole `produces` target.

**`variant_of` now spans tradeskills, not just combos within one.** Six items Pottery also crafts already had a Blacksmithing `recipe` node in this graph (Pot, Smoker, Skewers, Cake Round, Pie Tin, Muffin Tin), plus four Shaped Cookie Cutters that didn't yet (added alongside this work once their molds' real names resolved migration 375's original blocker — see migration 408). Each of Pottery's own combos gets a `variant_of` edge back to the pre-existing Blacksmithing anchor, exactly like same-tradeskill variant families (decisions/tradeskill-recipe-node-schema.md's "Recipe variants" section above) — nothing about `variant_of` ever assumed both ends belonged to the same trade, "same output item, different combo" doesn't care which tradeskill produced either combo.

**Caveat: `getRecipes()`'s variant grouping is scoped per-tradeskill, so a cross-trade `variant_of` edge doesn't currently surface as a visible "also craftable via X" hint on either card.** `getRecipes(tradeskill)` filters to that trade's own recipe nodes *before* grouping by `variant_of` family (`src/graph.ts`) — a Pottery recipe whose anchor is a Blacksmithing node still renders as its own full top-level card on the Pottery page (and vice versa on Blacksmithing's), rather than folding into the other trade's `variants` array. This is arguably the right UX already (each trade's page shows its own combo as a normal entry, not confusingly nested under an unrelated trade), so it wasn't changed — but the data-level relationship is real and discoverable by walking the edge directly, even though today's UI doesn't surface it.

**"OR" substitute ingredients that don't change the recipe's shape stay as one representative choice, not a variant family.** The Poison Vial family's pelt/skin slot accepts nine wiki-listed interchangeable substitutes (Low/Medium/High Quality Wolf Skin, Mist Wolf Pelt, various Cat Pelts, various Bear Skins, Zombie Skin, Crow's Special Brew) and the Deity Idols' Imbued Gem slot accepts any of 15 deity-specific gems — in both cases the combo's *shape* never changes, only which flavor of one ingredient goes in. Modeling every substitute as its own `variant_of` sibling would multiply these recipes 9x/15x for a distinction with no gameplay difference in how the recipe works; one representative ingredient is used instead (first-listed/cheapest), with the full substitute list recorded on that ingredient's own `source` field. This is a different call from the same-output-different-combo variant family above — that pattern is for combos that are actually differently shaped (different ingredient set, different trivial), not a single swappable slot.

**Cross-trade ingredients outside this graph's modeled tradeskills get a plain `item` node with a `source` note, no recipe/vendor backing.** Deity Idols' ingredient chain reaches into Poison Making (White Lead), an Enchanter spell (Large Block of Magic Clay, Vial of Clear Mana), and an NPC "Imbuer" service (turning an Unimbued Gem into an Imbued Gem) — none modeled in this graph. Rather than fabricate recipes for unmodeled tradeskills or skip the section entirely, each such ingredient is a real `item` node whose `source` field describes in prose how it's actually obtained; only the Pottery-side Wheel/Kiln steps are real `recipe` nodes.

Sourcing for all of the above: eqlwiki.com's raw wikitext via its MediaWiki API (`action=query&prop=revisions`, batched multi-title queries), not a summarizer — same bar as every tradeskill before it. Every vendor eqlwiki lists per ingredient is included (no capped/representative subset, per issue #51's own ask), skipping only zones not yet catalogued in this graph (same "zone not catalogued" precedent migration 381 used).

## Tailoring (issue #52): a page-level summary table isn't always as authoritative as the item's own page

Tailoring is by far the largest tradeskill modeled here — 278 recipes across 12 armor sets, bags/misc, quest items, and its own crafting stations (migrations 413-423), an order of magnitude past Brewing's ~78. Given that scale, most of this migration series sourced armor-piece AC/weight/ingredient-count data from `Skill Tailoring`'s own per-set summary tables (already captured in one raw-wikitext fetch of the whole page) rather than fetching all ~230 individual item pages — the summary tables give the same numbers an item's own page does, just batched.

**They aren't always identical, though.** A targeted post-hoc spot-check (re-fetching ~20 individual item pages, not the full set) caught one real disagreement: Ice Silk Robe's own page gives trivial 342 and a dedicated "Robe Pattern" ingredient, while the page-level Ice Silk Armor summary table said trivial 335 and (implicitly, via the shared per-slot pattern convention every other Tunic-slot piece follows) Tunic Pattern. Every other spot-checked item matched its summary-table data exactly. The individual item page is the more authoritative source when the two disagree — it's usually a smaller, more carefully-maintained page than the giant per-tradeskill summary table, which existing evidence (migration 423) confirms just made a transcription error listing the wiki's actual outlier. This isn't a reason to distrust summary-table sourcing generally (it held up on every other check), just a reason a spot-check pass is worth doing before merging a batch this large, rather than skipping straight to "the summary table already told me this."

**A second, systematic gap the same spot-check caught**: two of Tailoring's armor-set summary tables (Patchwork/Tattered, Studded) have no weight column at all, unlike every other set's own table — `weight` was correctly left unset per this doc's own "don't guess a field the source doesn't give" rule, but each piece's own item page does list a real WT value. Backfilled in migration 423 via one batched fetch of all 24 pieces' own pages. The lesson generalizes: a summary table's *absence* of a column doesn't mean the data doesn't exist, just that this particular table doesn't carry it — worth one targeted check before concluding a field is genuinely unavailable.

**Explicit "No Fail" quest combines are excluded, not modeled with a fabricated `trivial`.** Robe of the Lost Circle and Monk Training Bag (both Monk epic-chain quest assemblies) are on the wiki's own "Quest Items" table but explicitly marked No Fail — not a skill-check recipe this schema's `trivial`-driven success-threshold math (see above) has any field for. Same call applied to Glowing Crystalline Silk Piece, a No-Fail intermediate in the Coldain Prayer Shawl chain. A future tradeskill hitting the same "No Fail" wiki tag should exclude it the same way rather than inventing a placeholder trivial.

**A genuine sized-variant vs. an interchangeable-substitute slot look similar but aren't.** Reinforced Armor's Small/Medium/Large pelt choice gets 3 distinct item nodes per slot (real eqlwiki-given item names, real distinct weights) because the wiki treats them as 3 different items; Patchwork/Studded's own "1 Ruined Pelt" / "1 Medium Quality Pelt" language, despite superficially the same Wolf/Cat/Bear choice, stays a single representative ingredient (this doc's pre-existing "OR substitute ingredients" rule) because the wiki never gives the substitutes distinct item names or stats. The tell is whether the wiki's own table gives each option a distinct name/weight (variant) or just says "pick one" (substitute).

## Jewelcrafting (issue #50): a page-level summary table can mislabel the real ingredient, and sometimes the wiki genuinely doesn't know a fact

Jewelcrafting's 200 recipes (140 Basic gem+bar combos across Silver/Electrum/Gold/Platinum/Velium, plus 60 Deity-tier imbued-gem combos) surfaced two sourcing problems neither Tailoring nor any earlier tradeskill hit.

**The Crafters Item Table's "Metal" column names a tier, not the real ingredient.** Every Basic-tier recipe's stat block only appears when made with the *enchanted* bar (the page's own Basics section: "only enchanted versions have any bonus statistics"), but the column just says "Silver"/"Electrum"/etc., and roughly half of each non-Silver tier's individual item pages link the plain, unenchanted bar anyway -- a wiki-authoring shortcut, not a second recipe variant. Some of those pages carry an explicit corrective note ("Make sure to enchant the bar... or you will not get any stats"); the rest don't, but every one of them has a real stat block, which is only possible with the enchanted bar per the page's own stated mechanic. All 140 Basic recipes are modeled uniformly against the enchanted bar. The individual item page is still the source of truth for everything else (trivial, stats, weight) -- same "page's own item is more authoritative than the shared summary table" rule Tailoring established, just with one extra correction layered on top for this one field.

**Velium tier's own item pages mostly don't have a trivial at all** -- most literally say "Trivial: missing" in the wikitext. Here the *page-level summary table* is the more complete source (a full, internally consistent 220->302 progression that matches every individual page that does have a real number), the reverse of the usual page-wins rule. Two Velium items are also modeled under their canonical page titles (Black Pearl Velium Ring, Fire Emerald Velium Ring) rather than the summary table's stale redirect-source names (Blackened Pearl Velium Ring, Velium Fire Emerald Ring).

**Deity tier's own item pages don't know most trivials either** -- but unlike Velium, the summary table doesn't know them either (most cells are blank or a placeholder like "??", "?", `<217`, `>= 192`). This is a real gap in eqlwiki's own data, not a scraping failure. Per the project owner's explicit direction (2026-08-05) rather than leaving 45 of 60 recipes without a trivial (`recipe.trivial` is a required `number` used directly in `recipeSuccessThresholds()` and sort comparisons -- no "unknown" path exists in `src/graph.ts` today, and adding one was out of scope for a data migration): each item's own material Cost (also given by the Crafters Item Table) is interpolated against that same metal's Basic-tier Cost/Trivial curve, since Cost and Trivial track tightly within a metal -- confirmed empirically, since Deity items' Cost values land almost exactly on Basic-tier Cost values at matching price points. Validated against the 3 Deity items that *do* have a real wiki trivial: 2 exact matches, 1 off by 3 (183 vs. 186). The 4 Black Sapphire items (a rare mob-drop gem per the main page's own footnote) have Cost far above any Basic-tier item in their metal; naive linear extrapolation put Platinum's estimate at 381, above even Velium tier's own max, so those 4 are clamped to their metal's own Basic-tier ceiling instead of extrapolated. Every estimated recipe's `source` field says so explicitly ("Estimated trivial ... interpolated from material cost"), so the estimate is visible in the data itself, not silently indistinguishable from a wiki-sourced fact.

**Deity restriction and class restriction are two different fields, sourced two different ways.** `deity` (item-node-schema.md) comes from the Crafters Item Table's own Deity column, which is complete for all 60 rows even though several individual item pages omit their own `Deity:` statsblock line. `classes` stays unset (everyone) for every gem except Imbued Fire Opal/Solusek Ro, whose 4 items are Bard/Wizard-only per both the main page's own prose note and each item's own "Class: BRD WIZ" line -- deity restriction constrains who benefits from *wearing* the result, class restriction (rare here) constrains who can wear it at all; neither restricts who can *craft* it.

**No bonus/proc effect on any of the 200 items.** Every recipe was sourced from its own individual eqlwiki page (not just the summary table), and every one stops at the plain stat block -- confirmed by an explicit text-pattern check (`Click Effect`, `Proc Effect`, `Effect:`) across all 200 pages' raw wikitext, not just a spot check.

**No dedicated leveling-path table exists for Jewelcrafting** (unlike Brewing's own "Antonica Biased Brewers" table). Per the project owner's direction (2026-08-05: "maximum skill ups in the shortest amount of time for the least amount of ingredients and the least locations to travel to"), migration 431 derives one instead of leaving `levelingGuide` unset entirely. Every Jewelcrafting recipe already ties on ingredient count (exactly gem + bar, always 2), so that criterion doesn't discriminate; only 3 of the ~20 Basic-tier gems (Malachite, Carnelian, Wolf's Eye Agate) have any vendor (`sells`) data already in this graph, so "least travel" reduces to preferring those 3 over the loot/mob-drop-only alternatives that make up the rest of the tier. The leveling guide is exactly those 3 gems' recipes, one per metal tier, Silver through Velium (15 stops, trivial 17 through 250) -- restricted to Basic tier only, since Deity tier's own trivials are themselves cost-interpolated estimates, not a solid enough base to anchor a "recommended path" flag on.
