# Spell details partially sourced from the local client, not just eqlwiki.com

`scripts/scrape-spell-details.ts` now reads `mana`, `castTime`, `recastTime`, `range`, and `skill` directly from the locally installed client's `spells_us.txt` instead of the wiki, falling back to the wiki-parsed value when a local read isn't available. `description`, `spellType`, `resist`, `fizzleTime`, and `duration` stay wiki-only.

Field offsets (verified empirically the same way as the spell-line grouping above — this file's layout is an older two-file client format, message text lives separately in `spells_us_str.txt`, and doesn't match modern EQEmu documentation's field order 1:1):
- `mana` (field 14), `castTime` (field 8 / 1000), `recastTime` (field 10 / 1000): direct numeric reads, confirmed exact matches across many spells.
- `range`: field 4, **falling back to field 5 (aoerange) when field 4 is 0**. A naive "always use field 4" rule produced 50 wrong values (e.g. self/AE spells whose meaningful distance is their AE radius, not their zero target-range) out of ~668 checked; the fallback rule explains 99.1% of wiki values exactly. The remaining ~0.9% (6 spells, e.g. Curse, Kelin's Lucid Lullaby) were spot-checked against the *live* wiki (not just our repo's possibly-stale snapshot) to rule out "wiki is just outdated" before accepting them as residual noise — both spot-checks confirmed the live wiki agrees with our old data and disagrees with the local read, meaning these are genuine (small) local-extraction gaps, not staleness. Accepted as residual error, same spirit as "Faction data is approximate" above.
- `skill`: field 32, via a lookup table cross-validated against EQ's real canonical skill ID enum (4=Abjuration, 5=Alteration, 12=Brass, 14=Conjuration, 18=Divination, 24=Evocation, 41=Singing, 49=Stringed, 54=Wind, 70=Percussion). Diffing against the prior wiki-only data found this *fixing* real wiki-scraper bugs (garbled multi-field bleed from a template variant `extractField`'s regex didn't handle, leftover "†" footnote markers) far more often than introducing disagreements — only 1 genuine disagreement (`clinging-darkness`: wiki said Alteration, local says Conjuration) out of 9 changed values.
- `targetType`: tried the same lookup-table approach (field 30, 90.5% "accuracy" in isolation), but diffing the actual output caught it silently collapsing real distinctions the wiki preserves — worst case, `"PB AE"` (hits everyone around the caster) collapsed to `"Single"` (one target) for Kelin's Lucid Lullaby, which is a materially wrong answer, not a simplification. The 90.5% figure only measured "does the most-common category for this raw value match," which tolerates exactly this kind of lossy many-to-one collapse. **Reverted to wiki-only** — verified via a live (not cached) wiki fetch that this specific spell's `PB AE` value is current, not stale, so the disagreement is a real local-mapping limitation, not the wiki lagging behind.
- Not attempted: `resist`'s numeric modifier (the "(-30)" in "Magic (-30)"), `spellType`'s fine-grained categories (Heal/Cure/DoT/Slow/etc, vs. just the beneficial/detrimental split found at field 28), `fizzleTime`, and full `duration` formula resolution for the `description` field's `%z`/`#N`/`@N` placeholders — all blocked on the client's effect-slot fields (`effectid`/`base`/`base2`/`max[12]`), which statistical field/value correlation couldn't locate reliably (small-integer collisions across dozens of unrelated fields). The duration formula *itself* was recoverable (EQEmu's open-source `CalcBuffDuration_formula`, cross-referenced from their public GitHub source — not from decompiling the client's actual compiled `eqgame.exe`/`eqmain.dll`, which would be a meaningfully different and legally riskier act than reading a plain-text data file) and verified at 71.6% exact-match against known wiki durations, with the remaining gap concentrated in bard songs (consistently off by exactly 1 tick — a distinct mechanic EQEmu's generic buff formula doesn't capture) and a few DoT lines. Not shipped — 71.6% wasn't judged reliable enough to replace existing wiki duration data.

Before believing any client-vs-wiki disagreement is "the wiki is stale" (this repo's established default assumption per the Ward Undead case below), check the *live* wiki page directly rather than only this repo's cached `data/spell-details.json` snapshot — our own snapshot can itself have drifted independently of anything this session touched. Case in point: live-checking Curse's page (last edited 2026-07-06) surfaced its mana cost is now 212 on the wiki, while our repo's snapshot still has an older value — a real, unrelated drift worth a future full re-scrape, not something this session's local-data change caused or fixed. (The local client's `mana` field already reads 212 — matching the live wiki, not our stale repo snapshot — so the local-sourcing switch incidentally fixed this one on its own.)

Also checked eqlwiki.com's own Patch_notes page (covering 2026-05-22 through 2026-07-07) for all six spells with a residual range/skill mismatch — none appear in any patch during that window, ruling out "this is a recent balance change the wiki hasn't caught up to yet" as the explanation. Confirms the residuals are genuine (small) gaps in the local field mapping, not a wiki-lag artifact.

Since this repo is public, no local EQ install path is ever hardcoded in a committed script — `scripts/extract-spell-lines.ts` and `scripts/scrape-spell-details.ts` both take the install directory as a required CLI arg or `EQ_INSTALL_DIR` env var, with no default.
