# Quest lines: a `quest_line` node, reusing the `member_of` edge

Building out the leveling guide's "Armor of Ro" reference exposed a modeling bug: it was split into two independent `quest` nodes (a generic "Armor of Ro" and a separately-discovered "Mold of Ro Bracer"), when eqlwiki.com's `Armor_of_Ro_Quests` page is actually **one questline with seven independent sub-quests** — each its own NPC/zone/faction/turn-in, all sharing one page, one class/level gate, and one final crafting mechanic (combine a piece's Mold of Ro with a shared Bar of Ronium at a non-cultural forge).

Fix: a `quest_line` node type, and `quest --member_of--> quest_line` — the exact same edge type `spell --member_of--> spell_line` already uses (migration 019, `decisions/spell-line-filterable-dimension.md`) to group spells into progression lines. No new edge type needed; "these are members of a named line" is the same relationship whether the members are spells or quests.

`npc --starts--> quest_line` is also reused (same edge type as `npc --starts--> quest`) for the questline's own overview-level giver (Lord Searfire, who runs the shared Bar of Ronium crafting step), same reasoning as `rewards` already being reused for both item and faction targets — one edge type, disambiguated by the target node's own `type`.

Each of the seven sub-quests still carries its own `classes`/`minLevel` even though it's identical across the set (Paladin, 30+) — fields aren't inherited through `member_of`; `getQuests()` filters directly on each quest node's own fields, so a sub-quest that didn't restate them would incorrectly show up under "no class filter" as available to everyone. `quest_line` nodes carry the same fields for their own display purposes but don't feed into quest filtering directly — `getQuests()` only ever returns `quest` nodes, with the parent line resolved as metadata (`QuestSummary.questLine`).

A sub-quest rewards **two** items: the raw Mold of Ro piece (the sub-quest's literal, wiki-stated reward) and the finished armor piece (obtained by combining that mold with the shared Bar of Ronium — a separate crafting action, not a second NPC turn-in). Modeling both as `rewards` edges on the same quest node is a deliberate simplification: this graph has no `crafted_into`/similar edge type to represent "mold X becomes item Y through crafting" as its own relationship, so listing both under the same quest is more useful (you can see what you actually end up wearing, not just the intermediate reagent) at the cost of blurring "direct reward" vs. "reward one more step later." If a second real crafting-chain quest ever needs this, that's the point to introduce a real `crafted_into` edge instead of stretching `rewards` further.
