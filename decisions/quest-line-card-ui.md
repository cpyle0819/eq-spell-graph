# Quest-line card replaces its members in the results list

A `quest_line`'s member quests (see `decisions/quest-line-node-type.md`) don't each get their own card in the Quests tab's results list — that's the exact clutter (7 near-identical Armor of Ro cards) the `quest_line` node type exists to fix. Instead `quests.js` renders one `<quest-line-card>` per line and excludes any quest whose `questLine` is already represented by one (falls back to a plain `<quest-card>` if a member's line somehow wasn't returned by `/api/quest-lines` — a safety net, not the normal path). Search matches against a line's own name *or* any member's name (`questLineMatches()`), since a member's card only exists nested inside its line's now.

`<quest-line-card>` reuses `quest-card.js`'s exact section markup (Description/Starts In/Steps/Rewards, the header-badge row, the item-hover-tooltip wiring) via a new shared module, `public/components/quest-shared.js` — both need it identically, and `card-base.js` stays domain-agnostic (shared by non-quest cards too), so quest/item-specific-but-shared logic lives in its own module rather than either card-base.js or a cross-import between the two leaf cards.

**Roster rows use native `<details>`/`<summary>`, not `<collapsible-section>`.** `<collapsible-section>` (`public/components/collapsible-section.js`) was considered first — it already does exactly this disclosure pattern for the sidebar filter groups. Rejected because its header is a plain `label` string attribute (textContent only), and a roster row needs rich inline content (a seal, the quest name, its giver, a reward preview) that attribute can't carry — widening that component's contract to accept HTML risks its existing sidebar usage for a need specific to this one card. `<details>`/`<summary>` gives the identical semantics (keyboard-operable, no JS state — CSS reads the native `open` attribute) without touching a shared component. The chevron marker is redrawn to match `collapsible-section`'s own visual convention (▾, rotated -90° closed) since `<summary>`'s native marker is hidden — same look, different mechanism.

**Roster seals carry no numeral**, unlike `quest-card`'s Steps seals. Steps are numbered because their order is real (talk to the NPC before you can turn in the ore); a questline's members have no order between them — same wax-seal material, deliberately blank, so the *absence* of a number is itself the signal, not an inconsistency (see `quest-line-card.js`'s own header comment).
