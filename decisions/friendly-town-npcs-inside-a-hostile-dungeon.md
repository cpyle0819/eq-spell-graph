# Friendly town NPCs inside a hostile dungeon: sort by real signal, don't exclude wholesale

A dungeon-zoned bestiary batch (Crystal Caverns, issue #41) surfaced a shape not seen in prior batches: a hostile dungeon with a whole friendly settlement embedded in it (Froststone, the Coldain remnant town), sourced from the same `Category:<Zone>` / `{{Namedmobpage}}` sweep (`decisions/eqlwiki-mediawiki-api-for-messy-bestiary-categories.md`) as the zone's real mobs. The first pass through this batch excluded all 19 Froststone candidates wholesale as "not a mob," without checking whether any of them fit one of the graph's *other* npc roles, and without surfacing that call before shipping it. That was wrong on both counts: the fix is to route each candidate to the role it actually matches, and to ask before excluding anything outright.

**New role: `banker`.** Kramble Gemshard's own wiki description is "Banker in FrostStone" — a real, distinct service role, but not a `vendor` (a `vendor` in this graph always carries at least one `sells` edge; a banker doesn't sell anything, it stores). Added as its own `roles` value rather than folded into `vendor`. `src/graph.ts`'s `NpcSummary` doc comment, `scripts/audit-zone-npcs.ts`'s role-count object, and `public/components/zone-dossier.js`'s `ROLE_LABELS`/`CITY_ROLE_ORDER` all needed the new value added — a role isn't usable end-to-end just by existing in `data/graph.json`; it has to be in all three places that other roles are enumerated, or it disappears from the dossier UI and the audit's counts silently.

**`vendor` nodes selling mundane items, not just spells, is new but not unprecedented — it's the existing pattern extended.** Every `vendor` node in this graph before this fix sold only spells (verified: 0 of 563 existing vendors had a `sells` edge targeting an `item` node). The zone's own map key describes 4 unnamed "Merchant" NPCs (2 selling Alcohol, 2 selling "Food, Water, Bandages, and other Goods") with no wiki page of their own — labeled `"?"` since eqlwiki.com never named them, one node per NPC (never collapsed by goods type, even when two are mechanically identical). `sells` edges point at the real item nodes matching what's stated (`item:mead`, `item:ration`, `item:water-flask`, `item:bandages`). `src/graph.ts`'s `sellCategoryLabel()` already derives the dossier's sell-category text from the target node's own type generically (a `spell` target shows "Spells", anything else falls back to a pluralized type name) — no code change was needed for this part; it was already built to extend past spells before anything did.

**Guards are kept even with no known level; other roles without levels are excluded.** A `guard` role is a presence/defender signal independent of a level number (the zone's own page states its guards are "about level 34 or 35" as a description, separate from any per-NPC stat block) — so a guard-shaped NPC (a named "Guard `<name>`", or a title like "Captain" that implies the same rank) is added under `roles: ["guard"]` with `minLevel`/`maxLevel` omitted when the wiki gives no number, rather than excluded for lacking one. This is a real asymmetry from mobs (an unbounded/hedged level range still excludes a *mob* candidate, per the "An Evil Eye Pet" precedent in the MediaWiki API decision) — a guard's role is established by title and zone context, not by a stat block, so a missing level is just missing data, not missing evidence the NPC belongs.

**A named resident with no role signal at all still gets a node — `roles: []`, not exclusion.** Five Froststone residents (Cassia Gemshard, Derron Coldmist, Flint Velweaver, Fuller Velweaver, Nadalia Coldmist) came back from the wiki with nothing beyond a name and a "Citizens of Froststone" faction tag — no level, no description, no distinguishing title. Two more (Tacy MistHeart, Vevina Velweaver) had the same gap except a real, wiki-stated level. Both groups are added as bare `npc` nodes (name + `located_in` only, level kept when the wiki actually states one) rather than dropped — the graph is allowed to record "this NPC exists here" without knowing what it does yet, the same way a zone can be catalogued before its bestiary is. `NpcSummary.roles` can legitimately be `[]`; callers (the zone dossier's grouping) must not assume every npc lands in at least one role group.

**A quest tie promotes an otherwise-ambiguous townsperson to `quest_giver`.** Historian Baenek shares the same "Citizens of Froststone" faction tag as the plain residents above, but his own wiki description states a concrete quest role (turn in the Worn Coldain Tome; he has a stated respawn timer tied to that turn-in) — a real, checkable signal the plain residents lack, so he gets `roles: ["quest_giver"]` instead of the bare treatment. The same reasoning promoted "Soren Coldheart" (level 28, class Warrior, same faction tag as the named guards, despite lacking the "Guard" name prefix) to `roles: ["guard"]` rather than bare — a stated level + combat class is the guard signal, the name prefix is not required to carry it.

**Process note, not just a data-shape one: don't decide "exclude" unilaterally.** The original Crystal Caverns bestiary migration excluded all 19 of these candidates in one pass without flagging the call — the fix here (migration 323, following migration 322) exists because that should have been a question, not a silent decision. Any future batch that finds a candidate not cleanly a `mob` should surface the ambiguity — including proposing a new role category, the way `banker` came out of this one — rather than defaulting to leaving it out of the graph.
