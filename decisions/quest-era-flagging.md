# Quest era flagging

Quest nodes carry an optional `era?: string` — a plain content-era label like `"Kunark"` — matched by name against a new `era` node type (migration 032), not stored as an edge. Same reasoning as `class_levels.class` being a plain string rather than a forced edge to a (nonexistent) class node: an era, like a class, is a small, mostly-static taxonomy value a quest points at by name, not a rich entity a quest needs a graph relationship to.

`era` nodes hold the real ordering:

```ts
{ id: "era:classic", label: "Classic", order: 1, current: true, type: "era" }
{ id: "era:kunark",  label: "Kunark",  order: 2, current: false, type: "era" }
{ id: "era:velious", label: "Velious", order: 3, current: false, type: "era" }
```

Confirmed directly against eqlwiki.com (the Zones hub page lists "Classic", "Kunark (Out of Era)", "Velious (Out of Era)"; the wiki's own site-wide Era Filter / `{{Classic Era}}` template system confirms Classic is the one currently live) — not assumed from classic-EQ's real expansion history, which EQL doesn't necessarily follow (see CLAUDE.md). No era after Velious is documented on the wiki yet; the list grows by migration as EQL's progression actually advances and the wiki documents it, not ahead of it.

**Flagging rule** (`isOutOfEra()` in `src/graph.ts`): a quest's era is looked up against the era nodes' `order`; if it's strictly later than whichever era node has `current: true`, the quest is `outOfEra: true`. Same era or earlier is the explicit "do nothing" case — no field, no badge, nothing rendered. A quest with no `era` at all, or an era label that doesn't match any known era node, is also never flagged: unknown isn't evidence of "confirmed later than current," and guessing would produce false positives on quests nobody's actually verified yet.

**`outOfEra` is a real, live game mechanic**, not a data-quality warning invented for this app — eqlwiki.com already gates content this way (see the `{{Whichever Era}}` template note on the wiki's own main page: "Out of Era items or monsters or entries should not be removed! Utilize the Out of Era filter"). This app is just surfacing the same signal EQL's own wiki already tracks.

**No backfill.** None of the 11 real quests already in the graph got an `era` value in migration 032 — confirming a quest's real era requires checking that quest's own wiki page for its era tag, which is exactly the per-page verification work the "add all quests" GitHub issue tracks, not something to bulk-guess.

**Zones carry `era` too (migration 049), and quests inherit it.** An audit turned up quests sitting in confirmed-out-of-era zones (Firiona Vie, East/West Cabilis, Kael Drakkal, ...) with no `outOfEra` badge, because those zones weren't tagged and the quests' own pages didn't restate the era either. `zone.era` is the same plain-label convention as `quest.era`, verified against each zone's own page (`{{Kunark Era}}`/`{{Velious Era}}` template, fetched as raw wikitext — a summarized `WebFetch` briefly misgrouped Plane of Growth/Mischief on a first pass, which raw wikitext resolved). `resolveEra()` in `src/graph.ts` now computes a quest/quest_group's `era`/`outOfEra` as the worse of its own stated era and any zone it touches (`located_in`/`starts_in`) being confirmed out-of-era.

This is deliberately *not* the same "never infer" rule the paragraph above sets for a quest's own era — that rule is about not guessing an era from nothing. Inheriting from a zone's confirmed era isn't guessing; the zone's era is a hard, individually-verified fact, and a quest physically set there can't be earlier era than the zone itself. **Still no backfill of a quest's own `era` field** — inheritance is computed live in `resolveEra()`, not written onto quest nodes, so a quest's own `era` field still only ever reflects what that quest's own page actually states.

**UI**: `quest-shared.js`'s `outOfEraBadge()` renders a warning-styled badge (dark red, distinct from the neutral class/level badges — same "this is a caution, not metadata" register as `zone-card`'s kos/wont_sell faction badges, adapted for quest-card's light parchment background) only when `outOfEra` is true, composed alongside `headerBadges()` in both `quest-card` and `quest-group-card`. Quests/Maps also hide out-of-era results by default, behind an opt-in "Show Out of Era" `toggle-checkbox` — out-of-era content isn't actually reachable in the game's current era yet, so surfacing it unlabeled (or defaulting to shown) would recommend something the player can't act on.

Spell Finder's `rankZones()`/`zone-card.js` initially shipped without any of this (`ZoneRanking` had no `era`/`outOfEra` field at all) — a zone like East Cabilis could show up as a normal shopping destination with zero indication it's Kunark content ahead of the current era. Fixed by giving `ZoneRanking` the same `era`/`outOfEra` shape as `ZoneSummary`/`QuestSummary` (computed via the same `resolveEra()`), adding a `zone-card`-local `.era-badge` (same red, re-tuned for the card's dark-stone background rather than quest-card's parchment), and the same hide-by-default-plus-toggle treatment as Quests/Maps. **Any future page that surfaces zones needs this wired in explicitly — it does not come for free just because the underlying zone node has `era` set.**

That warning applied one level deeper almost immediately (issue #35): `getRoute()`/`shortestPath()` route *hops* had no era awareness at all, so a route could walk straight through an out-of-era zone as a pure waypoint (neither the "from" nor the "to" zone) with nothing to flag it — e.g. Dagnor's Cauldron → Butcherblock Mountains → **Firiona Vie** → Oasis of Marr, where Firiona Vie is Kunark content but only ever showed up as a plain arrow-and-name like any other hop. This is a genuinely different case from "is this result out of era" above: `RouteStep` needed its *own* `outOfEra` flag per hop, resolved in a shared `buildRouteSteps()` helper (used by both `getRoute()` and `rankZones()`'s own route-building, since `route-path.js` is shared by Maps' `route-card` and Spell Finder's `zone-card`) rather than only checking the endpoints. Issue #35 deliberately left it at that — flag the waypoint in place (`route-path.js`'s `.route-zone.out-of-era`, dotted underline + tooltip, same red), not hidden or rerouted around, on the reasoning that "a route only ever has one path to show for a given from/to pair."

**Issue #35's "flag it, don't reroute" call for waypoints was reversed by issue #38**, on the grounds that the Firiona Vie example isn't actually a single fixed path — it was just the *shortest by hop count*, and an in-era detour existed the whole time. `shortestPath()` now runs its BFS twice: first with out-of-era zones excluded as candidate waypoints (`bfsPath()`'s `skip` predicate), then — only if that first pass finds no route at all — a second, plain BFS with no era awareness, so a destination genuinely reachable only through out-of-era territory still resolves instead of reporting "no route." The `skip` predicate never applies to the destination itself, so routing *to* an out-of-era zone on purpose still works and still gets its badge via `resolveEra()`/`ZoneSummary`, same as before — this change is scoped to disqualifying out-of-era zones as *pure waypoints*, not to hiding out-of-era zones as valid destinations. `route-path.js`'s per-hop `outOfEra` badge is unchanged and still fires — it just now only shows up in the fallback case, where no era-clean route exists at all.
