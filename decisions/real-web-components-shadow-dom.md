# Real Web Components (Custom Elements + Shadow DOM), not string-template helpers

`public/components/*.js` are native custom elements with `attachShadow({mode:"open"})` and one `adoptedStyleSheets` `CSSStyleSheet` built once per class, not inline `<style>` tags. `theme.css`'s `:root` CSS custom properties (`--stone-1`, `--gold`, `--ink-muted`, etc.) are the theming contract — they inherit through shadow boundaries natively, so no redesign was needed there. Each component's shadow stylesheet is prefixed with `RESET_CSS` (`public/components/reset.js`) since `theme.css`'s `* { margin: 0; padding: 0; box-sizing: border-box }` reset can't reach inside a shadow root.

**A `:host` rule always loses to a same-target outer-document rule at normal priority, regardless of specificity** — confirmed empirically, not just by spec-reading (e.g. `:host { padding: 14px 28px }` rendered as `0px` because the reset's `*` selector also matches the custom element itself, a real light-DOM element). Any `:host` declaration for a property the page might set from outside needs `!important` (see `route-card.js`, `zone-card.js`, `mana-bar.js`, `spell-tooltip.js`, `tag-input.js` for examples). Where a *page* legitimately needs to override a nested component's own default (not fight an accidental reset collision), the pattern is a CSS custom-property escape hatch, not a plain property override: e.g. `mana-bar.js`'s `width: var(--mana-bar-width, 150px) !important`, set from a parent's shadow stylesheet via `mana-bar { --mana-bar-width: 100%; }` (`status-panel.js`) — custom properties inherit normally and aren't subject to the quirk above.

**The same quirk applies to `::slotted()`, not just `:host`.** Slotted light-DOM children (e.g. `welcome-scroll.js`'s slotted `<p>` paragraphs) are real light-DOM nodes theme.css's page-level `* { margin: 0 }` reset reaches directly, and that outer rule wins over a `::slotted(p) { margin-top: 10px }` shadow-tree rule at normal priority regardless of specificity — confirmed empirically the same way (the paragraph gap silently rendered as 0 without `!important`). Note `::slotted()` only accepts a single compound selector, no combinators — `p + p` (only non-first children get spacing) becomes `::slotted(p) { margin-top: 10px !important }` plus `::slotted(p:first-child) { margin-top: 0 !important }`, not a `+`-combinator selector. Properties the reset doesn't touch (font-size, line-height, color, flex, align-self, ...) style slotted content normally, no `!important` needed — see `welcome-scroll.js`/`tool-card.js`.

**Module-import order is load-bearing.** Every page's own script (`app.js`, `class-browser.js`, `route.js`) is `type="module"` with `import "./components/index.js";` as its first line — ES module import semantics guarantee the barrel fully executes (registering every custom element) before the importing script's own top-level code runs. Setting a JS property on a not-yet-upgraded custom element creates an instance property that silently shadows the class's own accessor once it *is* later defined, with no error — so getting this order wrong fails silently, not loudly. `components.js` (the legacy classic script holding the owned-spells localStorage helpers) stays a classic script; its globals are still readable from the modules.

**Delegated event listeners inside a component must attach to `this.shadowRoot`, not `this` (the host).** A listener on the host sees `e.target` retargeted to the host itself for anything inside its shadow tree, breaking `.closest()` class/attribute matching and making `e.relatedTarget` unreliable; a listener on `shadowRoot` sees the real internal target directly, since retargeting is a boundary-crossing concern, not one within a single shadow tree (`tag-input.js`, `zone-card.js`). Components never import sibling component files (`zone-card.js` uses `<route-path>` without importing `route-path.js`) — every custom element used anywhere is registered exactly once, by `public/components/index.js`, the single barrel every page loads.

**Components dispatch composed `CustomEvent`s for anything a page needs to react to**, rather than relying on a page-level delegated listener to class-match through a shadow boundary (which the point above rules out entirely once the interactive element is shadow-internal): `tag-input` fires `change`, `zone-card` fires `spell-owned-change`, `status-panel` fires `toggle-owned`/`clear-owned`. One exception stays deliberately un-componentized: `tag-input`'s suggestion dropdown is a plain node appended to `document.body` (styled by `theme.css`'s `.tag-dropdown`/`.suggestion-item`), since `position: fixed` already escapes the sidebar's `overflow: hidden` and shadow-nesting it would only risk an intervening stacking context breaking `z-index` for no benefit.

**A shared visual family (the Class Browser's `spell-card`/`aa-card`/`ability-card`/`stance-card`) extends a common `CardBase` class rather than each duplicating the same shadow-root/adoptedStyleSheets boilerplate.** `card-base.js` exports both the base class and a `BASE_SHEET` `CSSStyleSheet` built once; a leaf class's own `connectedCallback` (inherited, unoverridden) adopts `[BASE_SHEET, this.constructor.extraSheet]` when a leaf declares extra CSS (e.g. `spell-card`'s checkbox/vendor-list styling, which the other three leaves don't need) — `adoptedStyleSheets` accepts an array, and a `CSSStyleSheet` object can be adopted by many shadow roots at once, so the shared sheet's text is never duplicated per instance or per subclass. `home.html`'s `tool-card` (public/components/tool-card.js) needs the identical base panel look but isn't part of this family (never clickable, no badges/description/stats), so it duplicates its own small standalone copy rather than importing `card-base.js` — this codebase's convention is small, independent per-component CSS duplication (see `zone-card.js` duplicating `.spell-scroll`/`.spell-check`) with `CardBase` sharing only among truly-the-same-family siblings, not across unrelated pages.

**Phase 9 (final `theme.css` cleanup) found dead CSS accumulated across the whole multi-phase conversion, not just what each phase's own migration touched** — a full `grep`-based audit of every selector against every page's actual markup, not just the classes each phase happened to migrate. Found: `.filter-bar` (Class Browser's sidebar replaced it with `sidebar-panel` well before this conversion started, but the selector/comment lingered), the entire bare `button {}` bone-plate family + `.secondary` (every real light-DOM button had already become `.text-action`, and every other button lives in `macro-button.js`'s shadow root where an outer `button {}` rule can't reach anyway — it just took full componentization to make that total, not partial), `.results-header`/`.results-actions` (no markup references them at all), and `.field-group-label` (`collapsible-section.js` fully replaced its job). Takeaway for future cleanup passes: audit against actual usage each time, don't assume a rule is still live just because an earlier pass didn't flag it — dead code compounds silently across incremental migrations.
