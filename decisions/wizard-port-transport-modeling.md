# Wizard Port: modeled as edges, excluded from pathfinding by default

Issue #43 assumed the Planes (Fear, Sky, Hate) needed a "special access" transport type because they had no ordinary routes in the graph. Checking eqlwiki.com (Plane_of_Fear, Plane_of_Sky) showed that assumption was only half right: each has an ordinary, walk-through portal any class can use (a one-way portal in The Feerrott's spectre caves for Fear; an orb in East Freeport for Sky) — those are plain `connects_to` edges with `transport: "portal"`, always part of pathfinding, added by migration 364. **Both are one-way in only**, East Freeport → Sky and Feerrott → Fear — see the footgun note below before ever adding a return edge.

Separately, each Plane also has a redundant, Wizard-only group-teleport spell (`spell:alter-plane-sky`, level 46, consumes a reagent). That's the actual "Wizard Port" the issue named. It's modeled as `connects_to` edges with `transport: "wizard_port"`, one added from every other zone straight to the destination Plane (migration 364) — a cast-anywhere group teleport isn't zone-adjacency in the usual sense, so instead of special-casing "reachable from any zone" in the pathfinding code, every zone gets its own edge, keeping `shortestPath()`/`getZoneAdjacency()` ignorant of the distinction beyond a transport-type filter.

**Footgun, already hit once:** a first attempt added a return `Plane of Sky → East Freeport` portal edge too (reasoning: "falling off an island zones you back to East Freeport's ocean, so it's two-way"). Combined with the wizard_port fan-in, that turned Plane of Sky into an accidental teleport hub — `getRoute("Great Divide", "East Freeport", { includeWizardPort: true })` came back as a bogus 2-hop route (fly to Sky, walk the portal back) instead of the real 4-hop overland/boat route. Falling off an island is an accident-recovery mechanic, not a deliberate route back, and it shouldn't be modeled as one. If a real two-way connection to a wizard_port destination is ever justified, verify hop counts from several distant zones to that destination's own hub zone before shipping it, specifically watching for this shortcut pattern.

`getZoneAdjacency()` excludes `wizard_port` edges unless a caller passes `includeWizardPort: true` — threaded through `shortestPath()`, `getRoute()`, `getZoneDistances()`, and `rankZones()`, and exposed as a `wizardPort=1` query param on `/api/route`, `/api/plan`, `/api/zone-distances`. Default-off because assuming a Wizard is in the group isn't a safe default for a general route; the Maps and Spell Finder pages both expose an "Include Wizard Port" toggle (a `<toggle-checkbox>`) so a route can be compared with and without it, per the issue's original ask.

Plane of Hate has the identical real-world pattern (portal in Oasis of Marr + `Alter Plane: Hate`) but isn't in the graph yet (no NPCs/quests authored for it) — if it's ever added, it should get the same treatment: an ordinary portal edge plus wizard_port fan-out edges, not a reason to revisit this model.
