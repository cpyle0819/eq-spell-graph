# Wizard/Druid Port: modeled as edges, excluded from pathfinding by default

Issue #43 assumed the Planes (Fear, Sky, Hate) needed a "special access" transport type because they had no ordinary routes in the graph. Checking eqlwiki.com (Plane_of_Fear, Plane_of_Sky) showed that assumption was only half right: each has an ordinary, walk-through portal any class can use (a one-way portal in The Feerrott's spectre caves for Fear; an orb in East Freeport for Sky) — those are plain `connects_to` edges with `transport: "portal"`, always part of pathfinding, added by migration 364. **Both are one-way in only**, East Freeport → Sky and Feerrott → Fear — see the footgun note below before ever adding a return edge.

Separately, each Plane also has a redundant, Wizard-only group-teleport spell (`spell:alter-plane-sky`, level 46, consumes a reagent). That's the actual "Wizard Port" issue #43 named. It's modeled as `connects_to` edges with `transport: "wizard_port"`, one added from every other zone straight to the destination Plane (migration 364) — a cast-anywhere group teleport isn't zone-adjacency in the usual sense, so instead of special-casing "reachable from any zone" in the pathfinding code, every zone gets its own edge, keeping `shortestPath()`/`getZoneAdjacency()` ignorant of the distinction beyond a transport-type filter.

**Footgun, already hit once:** a first attempt added a return `Plane of Sky → East Freeport` portal edge too (reasoning: "falling off an island zones you back to East Freeport's ocean, so it's two-way"). Combined with the wizard_port fan-in, that turned Plane of Sky into an accidental teleport hub — `getRoute("Great Divide", "East Freeport", { includePorts: true })` came back as a bogus 2-hop route (fly to Sky, walk the portal back) instead of the real 4-hop overland/boat route. Falling off an island is an accident-recovery mechanic, not a deliberate route back, and it shouldn't be modeled as one. If a real two-way connection to a port destination is ever justified, verify hop counts from several distant zones to that destination's own hub zone before shipping it, specifically watching for this shortcut pattern.

`getZoneAdjacency()` excludes `wizard_port`/`druid_port` edges unless a caller passes `includePorts: true` — threaded through `shortestPath()`, `getRoute()`, `getZoneDistances()`, and `rankZones()`, and exposed as a `ports=1` query param on `/api/route`, `/api/plan`, `/api/zone-distances`. Default-off because assuming a Wizard or Druid is in the group isn't a safe default for a general route; the Maps and Spell Finder pages both expose an "Include Ports" toggle (a `<toggle-checkbox>`/`<macro-button>`) so a route can be compared with and without it, per the issue's original ask.

Plane of Hate has the identical real-world pattern (portal in Oasis of Marr + `Alter Plane: Hate`) but isn't in the graph yet (no NPCs/quests authored for it) — if it's ever added, it should get the same treatment: an ordinary portal edge plus wizard_port fan-out edges, not a reason to revisit this model.

## Extended to every Wizard/Druid teleport-to-fixed-zone spell (issue #64, migration 398)

Issue #64 asked to "flesh out" this model to cover the rest of the Wizard and Druid teleport spell families, not just Alter Plane: Sky. Every such spell was audited (Wizard: Gate/Portal/Translocate/Evacuate/[Markar's|Tishan's] Relocation; Druid: Ring/Circle/Zephyr/Succor) and deduped by *destination* — if any spell in a class's family reaches a zone, that zone gets one fan-out edge for that class (`wizard_port` or `druid_port`), regardless of which specific spell (self/group/single-target/emergency) actually does it. The per-spell distinction (mana, reagent, reliability) isn't modeled at the edge level; it wasn't for Alter Plane: Sky either.

**Footgun specific to this extension:** four destinations (Northern Karana, Toxxulia Forest, Stonebrunt Mountains, Western Commonlands) are reachable by *both* classes. The shared migration helper (`_lib.ts`'s `addEdge`) dedups on `source+target+type` only, ignoring the `transport` attribute — so calling it for a `druid_port` edge to a zone that already got a `wizard_port` edge to it would silently no-op and drop the second edge. Migration 398 doesn't use `_lib.addEdge` for this reason; it has its own `addPortEdge` that dedups on `source+target+transport` instead, while still skipping a port edge entirely wherever the source zone already has an ordinary (non-port) route to that destination — the same reasoning migration 364 used to skip East Freeport for Plane of Sky, just computed per-destination instead of hardcoded.
