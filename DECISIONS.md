# Design Decisions

## Architecture

### Graph as source of truth
`data/graph.json` is canonical. All mutations go through `src/graph.ts`.

### Node types
Current: `spell`, `npc`, `zone`, `stance`, `invocation`. Future: `quest`, `item`. Generic typed nodes avoid schema changes when adding entity types.

### Stance/invocation nodes: single-page scrape, not per-entity
`stance` and `invocation` nodes (migration 016) carry `label`, `description`, and a `classes: string[]` array of full lowercase class names — no `level`, since both are granted at level 1 (unlike `spell.class_levels`, which pairs each class with a level). Unlike spell data (scraped per-spell, one wiki page per spell), all 18 stances/invocations live on a single eqlwiki.com page ("Stances & Invocations") as two summary wikitables. `scripts/scrape-stances.ts` fetches that one page via the MediaWiki API and parses both tables directly, rather than following per-ability links — there's only one page to fetch, so the batching/resume logic `scrape-spell-details.ts` needs doesn't apply here.

Table-cell parsing has to treat any wikitext line not starting with `|` as a continuation of the previous cell, not a new one — some descriptions (e.g. Divine, Empower, Offensive, Striker) wrap across multiple source lines inside a single cell, and a naive "keep lines starting with `|`" filter silently truncates them at the first line break.

### Stances/invocations cover a different, larger class roster than spells
The Stances & Invocations data includes **Berserker**, a class with no purchasable spells and no entry in migration 007's `ALL_CLASSES` or the spell-derived `/api/classes` roster (`scrape-spells.ts` already skips Monk/Warrior/Rogue for the same "no vendor spells" reason — Berserker is the same case, just not previously encountered since nothing referenced it). Rather than reconciling this into one shared class list, `/api/classes/abilities` derives its own roster directly from `stance`/`invocation`/`aa` node `classes` fields, independent of `/api/classes`. The two endpoints will keep diverging by design — don't unify them into a single "all classes" list.

### AA nodes: same single-page-scrape shape as stances/invocations, but with a `category`
Migration 017 adds an `aa` node type (Alternate Advancement) carrying `label`, `description`, `classes: string[]`, plus AA-specific `ranks` (number) and `cost` (a raw "N/N/N"-per-rank string — kept as text, not parsed into numbers, since some ranks are still unresearched "?" placeholders in the source wiki) and `category`: `"general" | "archetype" | "class" | "special"`, matching the eqlwiki.com "Alternate Advancement" page's own four sections. Like stances/invocations, this is one page covering every class (`scripts/scrape-aa.ts`), not a per-ability scrape.

The class roster embedded in `data/aa.json` is derived from the page's own "Class AAs" subsection headings (16 classes) rather than hardcoded, so General/Archetype/Special AA entries — which the wiki says apply to every class — stay in sync with whatever the wiki documents without a separate hardcoded list to drift out of date.

**Archetype AAs are tagged all-classes, not split by archetype group.** The wiki's Archetype AAs table has no per-class or per-archetype-group breakdown — its own prose says "every class ... has Archetype AAs, some classes have more than others" but doesn't say which classes get which entry, and there's no per-ability page (unlike spells) to find that detail elsewhere. Bucketing individual abilities into the classic EQ Warrior/Priest/Caster/Hybrid archetype groups would mean guessing which group grants each specific ability with no wiki evidence — so instead, all Archetype AAs get `classes` = every class, same as General/Special, and `category: "archetype"` is what keeps them visually separate in the Class Browser. This is an approximation in the same spirit as "Faction data is approximate" below — it can overstate what a given class actually has access to in-game. Revisit if eqlwiki.com ever documents the per-class breakdown.

A handful of class-specific AA names (e.g. "Quick Evacuation") are reused independently by more than one class with different tuning — migration 017 gives `category: "class"` nodes an id of `aa:{class}:{slug(name)}` rather than `aa:{slug(name)}`, so these don't collide.

### Edge semantics
- `npc --sells--> spell`
- `npc --located_in--> zone`
- `zone --connects_to--> zone` (bidirectional; enables BFS pathfinding)

Edges encode relationships, not containment. An NPC can be both vendor and quest giver without hierarchy conflicts.

### Spell class/level model
`spell.class_levels: [{class: "shaman", level: 9}, ...]` — an array because the same spell can be available to multiple classes at different levels.

### Transport is an edge attribute, not a node
`connects_to` edges may carry `transport: "boat" | "translocator"` (migrations 009, 013). `shortestPath()` tracks transport per hop rather than modeling boats/translocators as intermediate nodes, so a route can flag "this hop is a boat crossing" or "this hop is a translocator" without the graph needing dedicated node types for either.

### Translocator wins hop-count ties over boat (or walking)
`shortestPath()`'s BFS keeps the first route it discovers to each zone and never revisits a tie, so the real tie-break is which neighbor `getZoneAdjacency()` hands it first. Each zone's neighbor list sorts translocator-linked entries to the front for exactly this reason — an equally-short alternative via boat or on foot should never beat a translocator hop by accident of edge insertion order in `graph.json`. No zone pair currently has more than one transport option between the same two zones, so this has no effect on today's routes; it's there for whenever one does.

### Hop count is a proxy for travel effort, not real-world time
`shortestPath()` minimizes hop count, treating every `connects_to` edge as equally "costly" regardless of transport. In reality a boat hop takes real minutes (per eqlwiki.com, ~15 min dock-to-dock for Butcherblock<->Ocean of Tears<->Freeport) while a translocator hop is instant, so a route with more hops but more translocators can be faster in practice than a shorter one that's all boats or walking. Not modeled — would need per-edge time weights and a shortest-time search (Dijkstra) instead of plain BFS. Fine for now since most planner routes are short and boat-heavy detours are rare; revisit if that stops being true.

### This game (EverQuest Legends) has different zone connectivity than classic EverQuest
Don't assume classic-EQ knowledge (Project 1999, Allakhazam, etc.) applies here — verify against eqlwiki.com specifically. Case in point: classic EQ has no Qeynos-side translocator, but EQL added one between East Freeport and South Qeynos in a May 28, 2026 patch (1pp/level fee, not modeled — the planner optimizes for hops, not cost). Zone names, connectivity, and NPC services can all diverge from classic EQ, sometimes recently and without the wiki being fully caught up yet — cross-check multiple pages (individual zone pages *and* patch notes) when something seems off, since new content can lag its own zone-page documentation.

The same "don't trust classic-EQ memory" warning applies to spell tuning, not just zones — e.g. Ward Undead (Paladin L1) showed "35 and 41 damage" in our data, which didn't match live-EQ memory of the spell. Investigated by fetching eqlwiki.com's live page directly: at the time, the wikitext's own two fields *disagreed with each other* — the free-text `description` field said "inflicts 12 damage" while the structured `{{SpellSlotRow}}` effect table said "Decrease Hitpoints by 35 (L5) to 41 (L11)." Our scraper (`scripts/scrape-spell-details.ts`) pulls the `description` field verbatim, and our stored value ("between 35 and 41 damage... 1.37 DPM") matched neither of the wiki's current fields — meaning the wiki's prose had been edited (likely a rebalance) sometime after our last scrape. Not a scraper bug: the scraper faithfully copies whatever the `description` field says at scrape time.

Re-ran `scripts/scrape-spell-details.ts` from scratch (deleted `data/spell-details.json` first — the script resumes from whatever's already in that file, so a normal run only backfills spells missing entirely, it won't refresh stale ones already present) and re-applied migration 011. Ward Undead now correctly reads "12 damage," matching the wiki's current prose. This wasn't an isolated case: **223 of 1,059 spell descriptions changed** in that one re-scrape, mostly the wiki collapsing damage/heal *ranges* down to a single number (e.g. "healing between 47 and 65 hit points" → "healing 65 hit points") and trimming long lore paragraphs to one-liners — reads like a site-wide editorial pass on the description template, not one-off rebalances. Lesson: this data goes stale faster than expected and drifts in bulk, not just spell-by-spell — re-scrape periodically rather than only chasing individual reports, and don't assume a single wrong-looking number is an isolated scrape error.

### Planning and routing are separate concerns
`rankZones()` (shop planning: "where should I go?") and `getRoute()` (point-to-point: "how do I get from A to B?") are independent functions/endpoints even though both walk the same zone graph via `shortestPath()`. The Route Finder page (`public/route.html`) exists separately from the planner rather than folding routing into it, because "get me from A to B" is a distinct question from "where should I shop" and doesn't need faction or spell context.

### Read-only routes are shared; mutation routes are Bun-server-only
`src/api.ts` holds the GET route table (`/api/plan`, `/api/route`, `/api/spells`, etc.) and is imported by both `src/server.ts` (local Bun dev server) and `src/lambda.ts` (a Lambda entry point for whichever infra deploys this app) — one route table, no drift between the two entry points. The POST/DELETE mutation routes (`/api/spell`, `/api/npc`, `/api/node/:id`, ...) stay in `server.ts` only and are never bundled into the Lambda build: they have no auth, and a typical Lambda's filesystem is read-only at runtime anyway, so `graph.ts`'s `writeFileSync` would just fail there. Data changes go through migrations, run locally, redeployed as part of the next Lambda package — not through live mutation calls.

### This repo has no opinion on where it's deployed
`src/lambda.ts` takes `rawPath` as already relative to its own root — no hardcoded path prefix, domain, or any other deployment detail. Whatever sits in front of it (CloudFront, API Gateway, a reverse proxy) is responsible for path rewriting and routing; that's infra's job, tracked in whatever separate infra repo owns the actual deployment, not here. See `scripts/build-lambda.ts` for the packaging step this repo does own.

`graph.ts` resolves `data/graph.json`'s path via `fileURLToPath(import.meta.url)` rather than Bun's `import.meta.dir`, since the Lambda bundle runs under the Node.js runtime, not Bun.

## Faction System (EQ Domain)

### Three dimensions determine vendor access
1. **Race** — determines guard kill-on-sight (`kos`). An Ogre is KOS in Kaladim for being an Ogre, regardless of deity.
2. **Primary class** — determines merchant refusal (`wont_sell`). Necromancer and Shadow Knight trigger this in good-aligned cities.
3. **Deity** — compounds with class. Evil deities (Innoruuk, Cazic-Thule, Bertoxxulous) cause `wont_sell` in good cities; good deities cause it in evil cities. Deity primarily affects religious-faction NPCs; race affects guard/civilian factions.

The planner resolves the **worst** standing across all three: `kos > wont_sell > neutral > safe`. Race and Deity each have a sentinel value, `"any"`, that removes just that one dimension from the computation — a real standing from the other two still applies normally. See "'Any' race and 'Any' deity" under UI below.

### Secondary class does NOT affect faction
In EQ, only primary class restricts deity selection, and only deity + race drive faction hits. Taking Necromancer as a secondary class avoids the faction penalty because deity choice remains unrestricted. This is why the UI has separate "Primary Class" and "Shopping For" dropdowns.

### Standing thresholds (eqlwiki Faction page)
| Standing | Range | Effect |
|----------|-------|--------|
| Scowls | -2000 to -751 | KOS |
| Threatening | -750 to -501 | KOS |
| Dubious | -500 to -101 | Won't sell |
| Apprehensive | -100 to -1 | Sells at bad prices |
| Indifferent+ | 0+ | Normal |

### Faction data is approximate
Standings are inferred from wiki research, not exact numerical values. Sufficient for route planning; not authoritative for edge cases like specific deity+race combinations.

## Data Coverage

### Spell data: all 12 classes
1,064 spells across bard, beastlord, cleric, druid, enchanter, magician, necromancer, paladin, ranger, shadow knight, shaman, and wizard (migration 008), superseding the original shaman-only (159-spell) dataset. The planner's "Shopping For" control is a multi-select — `rankZones()` takes a list of class names (plus optional pinned specific spells/zones) rather than a single class, so you can plan a shopping trip for more than one character's spell list at once.

### Spell detail enrichment
Migration 011 enriches spell nodes with description, mana cost, cast/recast/fizzle time, duration, target type, spell type, resist, and range (`scripts/scrape-spell-details.ts`); migration 012 cleans up a leftover "Skill:" prefix on the `skill` field from wikitext parsing. 1,059 of 1,064 spells have detail data (a handful of wiki pages didn't parse). Powers the spell tooltip in the planner and the detail cards on the spell browser page — cosmetic/informational only, not used in ranking logic. The script fetches the EQL wiki's MediaWiki API directly via plain `fetch()`, not a headless browser — this line previously (inaccurately) said "via Playwright," which hasn't been true of this script for a while; see the "Spell details partially sourced from the local client" entry above for the current mana/castTime/recastTime/range/skill local-vs-wiki split.

### Zone connectivity
88 zones (73 original + 15 classic dungeons added in migration 015), 47 of which have spell vendors, all reachable via bidirectional BFS. Migration 010 fixed two vendor zones (Ocean of Tears, High Keep) that had `sells` edges but no `connects_to` edges, making them unreachable.

### There is no non-stop Butcherblock<->Freeport boat
Migration 014 removed a direct `connects_to` edge between Butcherblock Mountains and East Freeport. Per eqlwiki.com/Ocean_of_Tears, that boat makes real stops at two islands inside Ocean of Tears (Zachariah Reigh Isle, then Sister Isle) — actual zone transitions, not a pass-through. The only route between them is via Ocean of Tears (two boat hops), which migration 010 already models. Worth remembering when auditing other "direct" boat edges: a boat connecting two named zones doesn't necessarily mean the trip is non-stop — check the wiki's actual route description, not just whether an edge exists.

### Dungeon zones use Project 1999 (classic EQ) data, not eqlwiki.com
Migration 015 added 15 missing classic dungeons (Befallen, Temple of Cazic Thule, Runnyeye Citadel, Lower Guk, Nagafen's Lair, Najena, Permafrost, Solusek's Eye, Splitpaw, Temple of Solusek Ro, The Hole, The Warrens, Kedge Keep, Mistmoore Castle, The Estate of Unrest), sourced from wiki.project1999.com instead of eqlwiki.com. This is a deliberate, user-approved exception to the "verify against eqlwiki.com specifically" rule above: the game is currently pre-Kunark, and classic dungeon geography/connectivity is assumed to match P1999 until eqlwiki.com coverage of these zones exists or proves otherwise. Kunark/Velious dungeons were intentionally excluded as out of scope for the current game era, even though some Kunark/Velious overland zones already exist in the graph. New dungeon zones carry no vendor data (classic dungeons are mob camps, not merchant hubs) and use the same "uninhabited wilderness" faction template as vendor-less overland zones (neutral race/deity standing, safe for all classes) rather than a scraped faction table.

### Naming mismatches
Some vendor data uses different zone names than adjacency data (e.g., "Neriak" vs "Neriak 3rd Gate"). Migration 005 bridges these with extra `connects_to` edges rather than renaming nodes (which would break existing edge references).

### Spell details partially sourced from the local client, not just eqlwiki.com
`scripts/scrape-spell-details.ts` now reads `mana`, `castTime`, `recastTime`, `range`, and `skill` directly from the locally installed client's `spells_us.txt` instead of the wiki, falling back to the wiki-parsed value when a local read isn't available. `description`, `spellType`, `resist`, `fizzleTime`, and `duration` stay wiki-only.

Field offsets (verified empirically the same way as the spell-line grouping above — this file's layout is an older two-file client format, message text lives separately in `spells_us_str.txt`, and doesn't match modern EQEmu documentation's field order 1:1):
- `mana` (field 14), `castTime` (field 8 / 1000), `recastTime` (field 10 / 1000): direct numeric reads, confirmed exact matches across many spells.
- `range`: field 4, **falling back to field 5 (aoerange) when field 4 is 0**. A naive "always use field 4" rule produced 50 wrong values (e.g. self/AE spells whose meaningful distance is their AE radius, not their zero target-range) out of ~668 checked; the fallback rule explains 99.1% of wiki values exactly. The remaining ~0.9% (6 spells, e.g. Curse, Kelin's Lucid Lullaby) were spot-checked against the *live* wiki (not just our repo's possibly-stale snapshot) to rule out "wiki is just outdated" before accepting them as residual noise — both spot-checks confirmed the live wiki agrees with our old data and disagrees with the local read, meaning these are genuine (small) local-extraction gaps, not staleness. Accepted as residual error, same spirit as "Faction data is approximate" above.
- `skill`: field 32, via a lookup table cross-validated against EQ's real canonical skill ID enum (4=Abjuration, 5=Alteration, 12=Brass, 14=Conjuration, 18=Divination, 24=Evocation, 41=Singing, 49=Stringed, 54=Wind, 70=Percussion). Diffing against the prior wiki-only data found this *fixing* real wiki-scraper bugs (garbled multi-field bleed from a template variant `extractField`'s regex didn't handle, leftover "†" footnote markers) far more often than introducing disagreements — only 1 genuine disagreement (`clinging-darkness`: wiki said Alteration, local says Conjuration) out of 9 changed values.
- `targetType`: tried the same lookup-table approach (field 30, 90.5% "accuracy" in isolation), but diffing the actual output caught it silently collapsing real distinctions the wiki preserves — worst case, `"PB AE"` (hits everyone around the caster) collapsed to `"Single"` (one target) for Kelin's Lucid Lullaby, which is a materially wrong answer, not a simplification. The 90.5% figure only measured "does the most-common category for this raw value match," which tolerates exactly this kind of lossy many-to-one collapse. **Reverted to wiki-only** — verified via a live (not cached) wiki fetch that this specific spell's `PB AE` value is current, not stale, so the disagreement is a real local-mapping limitation, not the wiki lagging behind.
- Not attempted: `resist`'s numeric modifier (the "(-30)" in "Magic (-30)"), `spellType`'s fine-grained categories (Heal/Cure/DoT/Slow/etc, vs. just the beneficial/detrimental split found at field 28), `fizzleTime`, and full `duration` formula resolution for the `description` field's `%z`/`#N`/`@N` placeholders — all blocked on the client's effect-slot fields (`effectid`/`base`/`base2`/`max[12]`), which statistical field/value correlation couldn't locate reliably (small-integer collisions across dozens of unrelated fields). The duration formula *itself* was recoverable (EQEmu's open-source `CalcBuffDuration_formula`, cross-referenced from their public GitHub source — not from decompiling the client's actual compiled `eqgame.exe`/`eqmain.dll`, which would be a meaningfully different and legally riskier act than reading a plain-text data file) and verified at 71.6% exact-match against known wiki durations, with the remaining gap concentrated in bard songs (consistently off by exactly 1 tick — a distinct mechanic EQEmu's generic buff formula doesn't capture) and a few DoT lines. Not shipped — 71.6% wasn't judged reliable enough to replace existing wiki duration data.

Before believing any client-vs-wiki disagreement is "the wiki is stale" (this repo's established default assumption per the Ward Undead case below), check the *live* wiki page directly rather than only this repo's cached `data/spell-details.json` snapshot — our own snapshot can itself have drifted independently of anything this session touched. Case in point: live-checking Curse's page (last edited 2026-07-06) surfaced its mana cost is now 212 on the wiki, while our repo's snapshot still has an older value — a real, unrelated drift worth a future full re-scrape, not something this session's local-data change caused or fixed. (The local client's `mana` field already reads 212 — matching the live wiki, not our stale repo snapshot — so the local-sourcing switch incidentally fixed this one on its own.)

Also checked eqlwiki.com's own Patch_notes page (covering 2026-05-22 through 2026-07-07) for all six spells with a residual range/skill mismatch — none appear in any patch during that window, ruling out "this is a recent balance change the wiki hasn't caught up to yet" as the explanation. Confirms the residuals are genuine (small) gaps in the local field mapping, not a wiki-lag artifact.

Since this repo is public, no local EQ install path is ever hardcoded in a committed script — `scripts/extract-spell-lines.ts` and `scripts/scrape-spell-details.ts` both take the install directory as a required CLI arg or `EQ_INSTALL_DIR` env var, with no default.

### Spell lines sourced from the locally installed client, not eqlwiki.com
Migration 019 adds a `spell_line` node type (`{label, type: "spell_line"}`) with `spell --member_of--> spell_line` edges, grouping spells into progression lines (e.g. Minor Healing → Light Healing → Healing → Greater Healing → Superior Healing; Yaulp → Yaulp II → Yaulp III). The wiki has no equivalent concept to scrape — this data came from `spells_us.txt`, a plain-text pipe/caret-delimited file shipped inside the locally installed EverQuest Legends client (the Daybreak Launcher's default per-machine install location), which is fair-game plain-text local data any player with the game has, same spirit as scraping a public wiki (see the entry above for why no install path is hardcoded anywhere in this repo).

Field 165 (of 173 `^`-delimited fields per spell row) is an undocumented per-spell "spell group" ID. Verified empirically, not from any public spec: every member of the cleric heal line shares one value (`100020020`), every member of Yaulp/Yaulp II/Yaulp III shares another (`100020200`), and unrelated spells have distinct values; the group-size distribution across all 73,957 client spell rows (1,930 distinct groups, mostly small clusters) is consistent with real line grouping rather than a coarse tag like expansion ID. **Not fully reliable** — Yaulp IV breaks from its line's shared value — so treat groupings as strong evidence, not a guaranteed-complete source; a missing line member is possible and not currently detected.

There is no separate "rank/tier" field in the client data (no clean 1,2,3,4 sequence found anywhere in a line's fields) — a line's node label is derived by finding the member with the lowest `class_levels` level and naming the line after it (e.g. "Minor Healing line"), since the raw group ID itself (e.g. `100020020`) has no human meaning.

`scripts/extract-spell-lines.ts` matches graph spells to client rows by name, then by scoring each candidate's per-class level array against the graph spell's own `class_levels` (client data has duplicate same-named rows for some spells — an NPC-only/all-classes-unusable variant alongside the real player-castable one — so a plain name match isn't enough to pick the right row). Outputs only the derived `data/spell-lines.json` (spell-group memberships for lines with 2+ matched graph spells: 202 lines, 888 of 1,064 graph spells) — never the raw `spells_us.txt` itself, since that's Daybreak's proprietary client data file and copying it wholesale into this repo is a different act than extracting a handful of already-public wiki facts. 1,053 of 1,064 graph spells matched a client row at all; 11 didn't (mostly apostrophe/naming variants like "Snail's Healing" or TLP-specific names like the "Al'Kabor" spiral line) and have no spell-line data.

## UI

### Planner-first
Primary use case: "where should I go to buy spells?" — a planning/table problem. Cytoscape graph view is a secondary exploration tab.

### EverQuest-themed skin lives in a shared `public/theme.css`
All three pages link one stylesheet for the classic-EQ (Velious-era stone UI) look, modeled on an original-UI screenshot: cool lavender-blue marble panels with SVG-turbulence veining, real two-tone bevels (4px panels, inverted on sunken wells), warm parchment inserts with dark ink (route paths, spell tooltip, Class Browser cards), bone/ivory button plates with dark serif caps sunk in a black groove, a five-bead mana-blue vitals bar for owned spells, Cinzel display serif via Google Fonts CDN, Georgia body text, and spell-gem chip bullets. Each page's inline `<style>` holds only its own layout. Textures are inline SVG data URIs (feTurbulence), not image assets — knobs documented in the CSS. Still no build step — it's a plain CSS file. Google Fonts is the only external dependency besides the Cytoscape CDN; the font stack falls back to Palatino/Georgia if it's unreachable. Faction badges use EQ /consider verbiage ("indifferent", "dubious", "scowls") with the practical meaning in a `title` tooltip — the header summary keeps plain language ("won't sell", "KOS") so nothing depends on knowing EQ slang. The reference screenshot lives at assets-cdn.daybreakgames.com/uploads/dcsclient/000/000/108/481.jpg.

### Scroll rollers: reserved for single-instance parchment, not the whole family
Fetched and inspected the actual reference screenshot (assets-cdn.daybreakgames.com/uploads/dcsclient/000/000/108/481.jpg) rather than working from memory of it — the real client's chat/scroll window has literal wooden dowel ends with metal ferrule caps at each side, a detail the original reskin hadn't captured. Added it (`--wood-1`/`--wood-2` tokens, `::before`/`::after` dowels) to `.route-path` and `#spell-tooltip` only — both are single-instance, transient surfaces (one route shown at a time, one tooltip on hover). Deliberately *not* applied to `.spell-detail` (Class Browser cards): those render dozens at once in a stacked list, and a wood dowel on every single one would read as repetitive clutter, not craft, undermining the "pages of a spellbook" metaphor those cards already have. Two different parchment idioms for two different real-world objects (an unrolled scroll vs. stacked book pages), not an inconsistency.

**Superseded** once Class Browser cards were rebuilt as a stone-panel-plus-parchment-scroll (`.spell-detail` + `.spell-scroll`, see below) — at that point the "book page" framing this exclusion depended on no longer applied; `.spell-scroll` *is* the same kind of object as `.route-path` (a scroll insert nested in a stone panel), not a flat page. After seeing the panel-plus-scroll redesign without dowels, the user asked to share styles with Route Finder and bring the end caps back, so `.route-path` and `.spell-scroll` now share one CSS rule (base parchment style + `::before`/`::after` dowels) instead of the dowels being route-only. Checked via Playwright at desktop and mobile widths across several stacked cards — the dowels stay clear of card edges and don't collide between packed cards, so the earlier clutter concern doesn't materialize in practice.

### Packed-card hover must brighten via `box-shadow`, not `filter`
`.zone-card` and `.spell-detail` share a 4px border with their next sibling via a negative-margin overlap (`margin-top: -4px`), relying on paint order so the later card's top bevel edge cleanly covers the earlier card's bottom edge — one shared seam, not two stacked borders. The original hover state used `filter: brightness(1.06)` (the same idiom as `.nav-link:hover`/`button:hover` elsewhere in the theme), but `filter` forces the element onto its own compositing layer, which desyncs that shared seam during the hover transition: for a few frames the hovered card's own (brightened) border shows through on top of its un-hovered neighbor's border instead of the normal single seam, rendering as a thick black double-line — reported by the user as "looks like something is broken" when moving the mouse off a Class Browser card. Reproduced and confirmed via Playwright screenshots at the mid-hover and 30ms-after-mouseleave frames (visible seam artifact), then confirmed gone after the fix. Fixed by brightening through `box-shadow` instead — added a fourth inset layer (`inset 0 0 0 999px rgba(255,255,255,0.05)`) on top of the existing two-tone inset bevel, since `box-shadow` paints in the normal flow and doesn't create a stacking context, so the seam never desyncs. `filter: brightness()` is still fine for non-packed elements (buttons, nav links) that don't rely on overlapping a sibling.

Also added, in the same pass: a slow, low-amplitude opacity animation (`body::before`, `torch-flicker` keyframes) on the warm overhead glow, meant to read as ambient torchlight rather than a UI transition — automatically disabled along with everything else by the existing `prefers-reduced-motion` rule, no separate opt-out needed. And the `.loading` state's text now has a spinning gem above it, reusing `.spell-chip`'s exact gem gradient rather than inventing a new spinner glyph — "the page is casting," not a generic loading spinner.

### Marble mottling raised from alpha slope 0.17 to 0.30
Fetched and zoomed into the reference client screenshot's stone panel (a flat, button-free strip, not the buttons or the scroll) and compared it side-by-side against a screenshot of our own `.controls-panel` at the same crop size: the reference shows clearly visible soft cloudy mottling even in plain stone areas, while 0.17 read as almost smooth at normal viewing size — the turbulence was present but too faint to register as "textured stone." Raised `--marble-tex`'s `feFuncA` slope to 0.30 (same turbulence shape/frequency/seed, just more visible), rather than changing `--stone-1`/`--stone-2` or the texture's frequency/type — this is one CSS variable shared by every stone surface (header, panels, cards, dropdowns, faction-tinted zone cards), so a single edit propagates everywhere with no risk of the family drifting out of sync. Deliberately kept the lavender-blue hue as-is; that's a documented, already-validated choice, not something this pass touched. Checked against real page content afterward (planner sidebar, header, Class Browser, mobile) — text stays fully legible against the busier texture since the average panel luminance is unchanged, only the local variance increased.

### Mana bar: five beads with bright seams — the vitals bars, not the group-list bars
The reference client draws two visually different HP/mana bars: the character vitals bars (top-right, under your own name — HP/mana/stamina) are a chain of distinct beads with a bright seam between each; the group member list's HP bars are one smooth continuous tube with no segmentation. `.mana-bar` tracks a single "spells owned" stat for one character, so the vitals-bar idiom is the correct one to copy — an earlier pass in this same session zoomed into the group-list bars by mistake, concluded the beading was an invented detail, and flattened `.mana-bar` into a smooth tube. Re-zoomed into an actual WinEQ2 classic-client screenshot of the vitals bars (user-supplied) and confirmed the beading is real: five segments, each with its own top-left specular highlight, separated by a bright ridge line (not a dark pinch — a common wrong guess, since a seam between two convex beads could plausibly go either way; the zoomed capture shows it's lit). Restored the tiled five-bead structure (`background-size: 20% 100%; repeat-x` for the specular and seam layers) with the seam corrected to a bright ridge flanked by slight shadow, rather than the dark-edges version an earlier build had guessed at. Color stays mana-blue rather than the reference's HP-red — that reinterpretation (this bar tracks spells owned, not health) is a separate, already-settled choice this pass didn't revisit.

### Spell Browser retired; spells are a Class Browser tab
`public/spells.html`/`spells.js` (a standalone page: one class, one level, free-text search, click-to-expand vendors) were deleted and folded into Class Browser as its first tab, once Class Browser already had a tab bar to put it in. The two pages' filter models don't actually match — Spell Browser is single-class + level-bound; Class Browser is up to three classes with no level filter, since stances/invocations/AAs are granted at level 1 and aren't leveled — so this isn't a straight merge:
- The **Level** field (`#level-field`, a plain `<select>` like Spell Browser's, not the planner's dual-range slider) only appears when the Spells tab is active; it's meaningless for the other six tabs and stays hidden for them.
- The **Search** field is generic and applies to whichever tab is currently active, filtering by name client-side — this works uniformly across all seven categories (Class AAs alone can run 30+ entries) rather than being a spells-only feature.
- `/api/spells?class=` now accepts a comma-separated class list (previously single-class only, since Spell Browser never needed more) and unions results by spell id, matching how `/api/plan` already handled multi-class. `getSpellsForClass()` itself stays single-class; the route handler loops and merges.
- Each spell card is badged per selected class with *that class's* level for the spell (e.g. "Shaman L9", "Druid L12") via an optional `levelLookup` callback on the shared `classBadges()` helper, rather than the old single `Level N` next to the spell name — necessary once a spell can be shown for more than one class at once.

### Spell cards link back to the planner
Class Browser's spell cards keep the "click to show vendors" inline list from the old Spell Browser (a flat list of NPCs/zones — no ranking, no route), but also add a **"Find in Spell Finder →"** link, since the planner is what actually answers "where should I go" (hop distance, faction, route) rather than just "who sells it." The link is a plain `<a href="index.html?pinSpell=<id>&pinName=<name>&levelMin=&levelMax=&classes=&race=any">` — no shared state store between pages, just a URL. `app.js`'s `consumePinnedSpellFromUrl()` reads those params on load, then strips the query string via `history.replaceState` so reloading or bookmarking the resulting planner URL doesn't re-trigger anything. Runs *after* `restoreState()` deliberately — that call fully overwrites `specificSpells`/level range/classes from localStorage, so applying the URL first would just get clobbered.

**Specific Spells is, and remains, an *exclusive* override — pin any spell and results narrow to only pinned spells, ignoring Shopping For classes entirely.** That part of the behavior was never the bug and a first attempt at this fix broke it: it changed pinning into a *union* with the Shopping For class list instead, so pinning a spell that Shopping For already covered had no visible effect at all — indistinguishable from the feature doing nothing. Reverted to the exclusive model.

What actually needed fixing: `rankZones()` used to narrow candidates by Shopping For class *first*, then narrow *again* to just the pinned ids — so a pinned spell outside the current class selection was already gone before the pin-narrowing step even ran, and its class/level pairs got filtered a second time on top of that by the level range. The fix reorders this: when any spell is pinned, candidates go straight to exactly the pinned ids (Shopping For classes are skipped, not intersected), and each pinned spell shows *all* of its real class/level pairs rather than only the ones that happen to satisfy `classNames`/`levels`. A pinned spell now always shows up correctly regardless of whatever Shopping For classes or level range happen to be saved — which is what actually matters for the Class Browser deep link, since Class Browser has no way to know what's currently saved in the planner's localStorage.

Since that fix makes the pin robust on its own, the URL's `levelMin`/`levelMax`/`classes` params are purely cosmetic — they keep the planner's *displayed* level range and Shopping For chips consistent with what you were just looking at in Class Browser (an empty/"All Levels" Class Browser filter maps to the full 1–`MAX_SPELL_LEVEL` range, not whatever narrow range happened to be saved), rather than being required for the spell to show up. Because pinning is exclusive, those chips end up inert once something is pinned (Shopping For plays no role in the results anymore) — that's an acceptable, honest side effect of an exclusive filter, not a bug: removing the pinned spell falls back to a Shopping For selection that actually matches what you were browsing, instead of a stale unrelated one.

### "Any" race and "Any" deity each neutralize only their own dimension
Both `race-select` and `deity-select` have an `any` option. Each is independent: picking Any for one still lets a real standing from the other (or from `primaryClass`) come through normally. This was not the first design — an earlier pass made `race=any` a blanket switch that forced every zone to `"safe"` and ignored primaryClass/deity too, on the theory that the Class Browser deep link (the only caller with no race/deity context at all) needed *something* neutralized to avoid a misleading stale result. That blanket version was wrong: it meant picking Any for race in the normal planner UI would also silently hide a real deity-driven won't-sell, which isn't what "I don't know my race" should mean — it should mean "don't let race penalize this," not "stop checking anything."

Corrected: `raceIgnored`/`deityIgnored` each just substitute `"safe"` for their own slot going into `worstStanding(raceStanding, classStanding, deityStanding)` — a real KOS from race still shows with `deity=any` set, and a real won't-sell from deity still shows with `race=any` set. Confirmed both directions: Ogre race (real KOS) + `deity=any` still surfaces "19 zone(s) KOS"; `race=any` + an evil deity (real won't-sell) still surfaces "N zone(s) won't sell to you." Since the resulting `faction` is now always a genuine (if partial) evaluation, the frontend needs no special-casing at all — no more suppressing the green "safe" tint, no more forced "confirmed safe" fabrication. `ZoneRanking.raceIgnored`/`deityIgnored` (each omitted unless true) only drive a small informational note ("race ignored" / "deity ignored" / "race & deity ignored") in the results header, telling you *why* a dimension isn't contributing, without implying the rest of the result is meaningless.

Deity data was confirmed to matter before adding this (not just assumed): 75 `wont_sell` and 2 `kos` results across the zone faction data (`data/graph.json`), e.g. Paineel is KOS to Mithaniel Marr/Tunare worshippers. So deity keeps its full option list — this is additive, not a replacement for real deity selection.

The Class Browser "Find in Spell Finder" link sets *both* `race=any` and `deity=any` unconditionally, since it has zero context for either — that's the one place a "blanket-ish" outcome is actually correct, just arrived at by two independent flags being true simultaneously rather than one flag forcing both.

**`<option value="any">` goes last in the Race `<select>`, not first.** A first pass added it as the first option, which — since `applyDefaults()` never explicitly sets `race-select`'s value, it just relies on the browser selecting whatever option is first — silently made "Any (ignore faction)" the default race for every first-time visitor, hiding real KOS/won't-sell warnings by default. Caught by a screenshot showing "Barbarian" wasn't selected when it should have been on a clean run. `deity-select` already had an explicit `selected` attribute on "The Tribunal" so this specific bug didn't repeat there, but the new option still went last for consistency. Any new option added to a `<select>` that has no explicit default assignment needs the same check: does skipping the explicit-default code path change what a fresh visitor sees?

### Primary Class also has an "Any (ignore faction)" option; all three faction fields now default to Any
Primary Class was the odd one out — Race and Deity both had `any`, Primary Class didn't. Added `<option value="any">` (last, same convention as above) and a matching `classIgnored` on `ZoneRanking`/`rankZones()` (`src/graph.ts`), mirroring `raceIgnored`/`deityIgnored`: substitutes `"safe"` for `classStanding` in the worst-of computation, only neutralizing its own dimension — a real class-driven wont_sell/kos still shows through when race/deity are Any (and vice versa), confirmed by setting `primaryClass=necromancer` with race/deity at Any and seeing "18 zone(s) won't sell to you" persist. The results-header note now lists any/all of "race, class & deity ignored" rather than just the two.

Once Primary Class could be Any, the actual defaults changed too: Race/Primary Class/Deity now all ship `selected` on their `any` option, replacing the old Barbarian/Shaman/The Tribunal starting point (`resetFilters()`'s hardcoded values updated to match). Rationale: these three fields only affect vendor faction standing, not which spells show up (see the sidebar's "Faction" section tooltip) — defaulting to three arbitrary specific values suggested they mattered more than they do, and silently applied someone else's faction profile to every fresh visitor. Any *existing* visitor's `localStorage`-persisted state is untouched by this — `restoreState()` still wins over `applyDefaults()` when present, so this only changes what a first-time visitor (or someone who clicks Reset filters) sees.

### Planner state: single auto-saved snapshot, not named profiles
The planner persists one last-used state (race, class selections, deity, zone, level range, pinned spells/zones, owned spells) to `localStorage` and restores it on load — it does not support multiple named/saved characters. This replaces an earlier per-character profile system (named profiles, per-profile owned-spell tracking) with something simpler for the common case of planning for one character at a time. Revisit if multi-character support turns out to matter — the per-profile version demonstrated it's a straightforward layer to add back on top of `getState()`/`restoreState()`.

### "All owned" needs its own empty state, distinct from "no results"
`renderRankings()`'s zone loop silently `continue`s past any zone where every spell is already marked owned (when `showAllSpells` is off) — correct, since there's nothing left to show there. But nothing checked whether *every* zone got skipped that way: the results header (built from pre-filter counts) would still say "9 spell(s) across 20 zone(s)," and the area below it would just be empty, with no visible reason why. Tracked a `renderedZones` counter through the loop; if it's still zero afterward, append a `.no-results` message ("All matching spells are marked owned.") with a `Show all` button. That button reuses the header's own toggle rather than a one-off — `#toggle-owned-btn`'s unique id was changed to a `.toggle-owned-btn` class so the same delegated click handler (matched by class now, not id) fires from either location, since two elements can't share one id on the same page.

### Reset filters: restore HTML defaults, don't blank the form
Added a "Reset filters"/"Reset" `.text-action` link to all three pages (Spell Finder, Route Finder, Class Browser). It restores each field to the value already baked into the HTML (Any/Any/Any faction + levels 1-10 on Spell Finder — see "Primary Class also has an 'Any (ignore faction)' option" above for why this isn't Barbarian/Shaman/The Tribunal anymore, `— None —`/All Levels/empty search on Class Browser, `— Select Zone —` on Route Finder) rather than clearing everything to empty — a populated, sensible starting point is more useful than a blank form, and it's what `applyDefaults()` already did for first-time visitors. Deliberately scoped to filter/search inputs only: it does not touch owned-spell marks on Spell Finder, since that's a separate, already-solved concern with its own "Clear owned" action.

### Class Browser search must not hide category tabs
`buildSections()` used the *search-filtered* item count to decide whether a tab existed at all (`.filter((section) => section.items.length)`), so typing a query that matched nothing in, say, Stances made the Stances tab disappear entirely while searching — losing track of which categories exist at all mid-search. Split each section into `allItems` (class-selection-filtered only, never touched by the search box — decides whether the tab exists) and `items` (search-filtered on top — decides the tab's count badge and what renders). A tab now only disappears when the category has zero items for the *class* selection (e.g. a caster has no Disciplines tab at all); searching just drives the count to "0" and the results pane to a "No {category} match your search" message, without touching tab visibility.

### Abilities tab: class-defining special actions, not spells/stances/AAs
Added a new `ability` node type and Class Browser tab for things like Rogue's poison disciplines, Backstab, Kick, Taunt, Bash, Hide, Sneak, Mend, Disarm, Pick Lock/Pocket, Disarm Traps, and the Monk kick-family specials (Round Kick/Tiger Claw/Eagle Strike/Dragon Punch/Tail Rake) — started from a GitHub issue asking for just Rogue disciplines, broadened after discussing scope: these are "press a button to do a specific named thing," distinct from spells (bought/learned), stances/invocations (level-1, no cooldown), and AAs (point-bought ranks).

**Shape:** `{ label, description, class_levels: [{class, level}], duration?, reuseTime?, category?: "combat" | "utility" | "special" }`. Uses `class_levels` (spell's shape), not `classes: string[]` + a single top-level `level` like stance/invocation/aa — several of these (Kick, Disarm, Hide, Sneak, Pick Lock) are granted to multiple classes at *different* levels each (e.g. Kick: Monk L1, Warrior L1, Ranger L5), so a single `level` field doesn't hold once the scope grew past Rogue-only. `duration`/`reuseTime` are left off entirely (not an empty string) when the wiki doesn't state one, rather than guessed.

**Two data sources, deliberately not scraped the same way:**
- Rogue poison disciplines (9 entries) come from a real scrape (`scripts/scrape-disciplines.ts`) of the wiki's single "Disciplines" page — confirmed by fetching the raw wikitext directly via the MediaWiki API that every other class's discipline table on that page is either empty or entirely wrapped in `<s>...</s>` ("not yet on Legends"); Rogue is the only class with live rows.
- The other 18 entries (Lay Hands, Harm Touch, and the "usable skill" list) are hand-curated, not scraped. Each lives on its own free-text "Skill X" wiki page with *no shared template* — confirmed by fetching several directly: Taunt's classes are a bullet list with inline patch-date notes and no level; Bash's classes are an inline abbreviation string up top *plus* a separate wikitable whose "Skill Cap" column is all zeroes (useless); Kick and Harm Touch use a clean "Level N (Max NNN)" bullet format; Hide/Sneak mix class-granted rows with race-granted rows in the same list. No single parser handles all of these — each entry's values were read off its page by hand (see migration 018's inline citations).

**Deliberately excluded:** generic weapon-proficiency/tradeskill/magic-school/musical skills (not a discrete named action, just a trainable number); Slam (racial — Barbarian/Ogre/Troll — not class-based, and has no "Classes" section at all on its wiki page); the racial-access rows on Hide (Dark Elf/Wood Elf/Halfling) and Sneak (Halfling), since the Class Browser is organized by class; Flying Kick (in scope discussion but not part of the approved list — add later if wanted).

**Sort order** (`/api/abilities` in `src/api.ts`): by whether the ability has a visible poison-type tag at all (Combat/Utility), then by that category, then by name. `"special"` (no badge rendered — see `renderAbilityCard` in `class-browser.js`) counts as *zero* categories and sorts first, ahead of any Combat/Utility poison — so Backstab, Disarm, Hide, Pick Lock, etc. lead the list, with the Rogue poisons trailing, Combat grouped together then Utility grouped together. (An earlier pass tried sorting by *number of classes granted to*, fewest first, as a proxy for "how signature does this feel" — reasonable in theory, but not what was actually meant by "fewer categories first": category here means the Combat/Utility tag, not class breadth.) This groups by whatever `category` values exist rather than special-casing poison names, so the same logic applies to every class.

`.text-action` (the plain muted-text-link style used for Show all/Clear owned) had only ever been defined in `index.html`'s page-specific `<style>` block, not in shared `theme.css` — reusing the class on Route Finder/Class Browser's Reset buttons silently fell back to the full bone-plate `button` styling instead (no visual bug until something outside Spell Finder tried to use it). Moved the rule into `theme.css` so all three pages share one definition; page-specific styles now only handle each Reset button's placement (`margin-left: auto` to pin it to the right edge of its row, consistent across pages regardless of how the row wraps).

### Faction LED dots and badges explain *why*, not just *what*
The zone-card faction indicator (an LED-dot `::before` pseudo-element on `.zone-name`, plus a `.faction-badge` for non-safe results) only ever showed what a standing means ("Scowls at you, ready to attack — kill on sight"), never why — race, class, and deity weren't distinguished anywhere in the API response, so a KOS or wont_sell result gave no way to tell which of the three caused it. `rankZones()` (`src/graph.ts`) now returns an optional `factionReasons: { dimension: "race"|"class"|"deity", value: string }[]` on each `ZoneRanking`, populated only for `wont_sell`/`kos` results (safe/neutral have nothing to explain) and only with the dimension(s) whose individual standing actually matches the overall (worst) one — so a wont_sell result caused solely by deity doesn't also blame class just because class happened to be present. The frontend appends these reasons to the existing tooltip text (`factionTooltip()` in `app.js`), e.g. "...kill on sight (your Troll race is disliked here)".

The LED dot itself still can't carry a tooltip directly (a `::before` pseudo-element has no DOM node to hang a `title` attribute off of) — the fix is a `title` on `.zone-name` itself, which covers the dot's hover area since it's positioned inside that span. Both `.zone-name` and `.faction-badge` now share the exact same tooltip text via one `factionTooltip()` call, rather than the badge computing its own and the dot having none at all.

### Spell Finder's zone-card: the spell list is the scroll now, not the route
Heuristic established by Route Finder (`.route-card` + `.route-path`) and Class Browser (`.spell-detail` + `.spell-scroll`): whatever content a page exists to show — the thing worth reading closely — goes in the parchment scroll insert; everything else is plain stone. On Spell Finder, that used to be backwards: the route between zones sat in the parchment scroll (`.route-path`), while the actual spell list (what you're there to find) sat directly on the stone panel with no scroll treatment at all. Swapped: the spell list now lives in a `.spell-scroll` (shared class from `theme.css`, same one Class Browser uses — dowels included), and the route is a plain-stone breadcrumb (`.zone-route`, page-specific to `index.html`) using the same icons/markup as before, just re-colored for a dark background instead of parchment (`.route-label`/`.route-steps`/`.route-zone`/`.route-sep`/`.boat-sep`/`.translocator-sep` are tuned for parchment ink in `theme.css` — needed light-on-stone overrides here). Side effect the heuristic predicts: each zone-card's height now genuinely varies with its spell count instead of being roughly uniform, breaking up the page the way stacked cards of different content naturally should.

`.spell-chip`/`.vendor-tag` needed the same light-vs-dark retuning, just in the opposite direction: they were a dark "sunken well" pill (near-black background, light text) designed for sitting directly on stone, and moving them onto the parchment scroll left a jarring dark-chip-on-light-page look — passed a raw contrast check (chip text vs. its own dark background was still ~14.7:1) but read as a harsh light→dark→light luminance sandwich rather than a contrast failure. Confirmed `.spell-chip`/`.vendor-tag` render nowhere else, so retuned them wholesale to the same tinted-background/dark-ink convention as Class Browser's `.type-badge`/`.mana-badge`/`.class-badge` (`.spell-chip`: 7.41:1, `.vendor-tag`: 6.44:1 against `--parch-bg`). The one real WCAG miss caught in the process: `.lvl`'s muted sub-label was still `var(--ink-muted)` (tuned for dark stone, 4.6:1 there) which measured only 3.89:1 on parchment at its 11px size — failed AA. Switched to the existing `--parch-ink-soft` token (4.65:1) rather than inventing a new muted tone.

### `#planner`'s marble backdrop needs `background-attachment: fixed`
On wide layouts `#planner` uses `overflow: visible` (needed so `.controls-panel`/`.status-panel` can `position: sticky` against it) rather than clipping and scrolling its own content — confirmed via `window.scrollY` vs. `#results`'s own `scrollTop` while scrolling that the *document* is what actually scrolls in that layout, not an inner `#results` container (its `overflow-y: auto` is a no-op there since its content is never taller than itself). That meant `#planner`'s own `background` (marble texture + lit-top/shaded-bottom gradient, default `attachment: scroll`) moved right along with the document scroll — visibly sliding as you scrolled, since it's repainted at the document's coordinates, not the viewport's. Fixed by setting `background-attachment: fixed` on just the marble-texture layer (`background-attachment: fixed, scroll` — the two values map to the two comma-separated images in `background:`), leaving the lit-top/shaded-bottom gradient tracking `#planner`'s own box as before, since that's shading one specific panel's real top/bottom edges, not something that should repeat every viewport height. `.zone-card`/`.controls-panel`/`.status-panel` keep default-attachment backgrounds on purpose — each is a physical object that should carry its own surface with it, unlike the backdrop behind/between them. Separately: no, `.zone-card` instances don't share one continuous painted background — each tiles the same marble texture independently from its own box origin. Not fixed, since it's a random turbulence noise pattern (translation-invariant-looking), so the seam between packed cards shows no visible discontinuity in practice.

### MacroButton: one shared component for every non-text button, socket + raised button, two bevels
Modeled on the reference client's bottom-left macro bar (assets-cdn.daybreakgames.com/uploads/dcsclient/000/000/108/481.jpg and a user-supplied crop, `~/Downloads/ui_buttons.png`), replacing both the old floating bone-plate `.nav-link` style and the first pass at a status-panel-only square button. `public/components.js` exports `MacroButton({ label, tag, href, id, className, square })`, returning a `.macro-socket` (recessed cavity) wrapping a `.macro-btn` (raised button or link) — every non-text button on every page renders through this one function: nav links (`tag: "a"`) and the status panel's Show all/Show remaining/Clear owned. `.text-action` (plain muted links like Reset filters, or the empty-results "Show all" fallback) is a separate idiom and doesn't use it.

Sizing: dynamic (fits the label) by default, since nav labels vary in length; pass `square: true` for a fixed 90×90 slot instead, e.g. the two status-panel actions sitting side by side, where they need to match each other's size regardless of label length. Both `.macro-socket`/`.macro-btn` use *pixel* dimensions when square (not `aspect-ratio`/`flex-grow`, which content can still push around) — labels over 10 characters get a `.long-label` font-size reduction instead, so the box size never changes, only the text does.

Light source is top-right for this whole component: the raised `.macro-btn` catches light top+right and shadows bottom+left; the recessed `.macro-socket` is the inverse — dark top+right (`#362c5a`), lit bottom+left (`--edge-hi`). The socket's inset shadows use blur (not 0-blur offsets) so the bevel actually sweeps around its `border-radius` instead of looking clipped at the corner.

**This was originally a deliberate exception** to a top-left convention `.zone-card`/`.controls-panel` used elsewhere — later reversed (see "Whole-app light-source consistency pass" below): MacroButton/MacroSocket turned out to be the one component already built correctly, and everything else got flipped to match it instead.

The button's own bevel is a second, independent effect on top of the socket's: `::before`/`::after` pseudo-elements painted with `mix-blend-mode: lighten`/`darken` (not fixed overlay colors) so it reads as brightening/dimming the button's actual gradient rather than painting a flat tint over it. Each fades from the button's own color back to white/black over 5px (6px for `.square`, since a bigger surface reads better with a slightly heavier bevel). `clip-path` confines each pseudo-element to an L-shaped region (its own two edges) so the light and dark bevels meet with a clean 45° miter at the corners, rather than the two independent per-edge gradients overlapping as a rectangle. `--bone-tex` (the marble turbulence recipe, reused at a different alpha) is layered into both the button face and the bevel pseudo-elements themselves, so neither is a mathematically perfect gradient — it's faintly mottled, matching the marble panels' own texture treatment.

`--bone-1`/`--bone-2`/`--bone-edge-hi` (the shared bone-plate face colors) were also lightened slightly toward white as part of this pass — a site-wide token change affecting every bone-plate surface.

### MacroButton's pressed state swaps which corner catches light
`.macro-btn:active` needs to read as physically depressed, the opposite of the raised default (top+right lit, bottom+left shadowed — see above). Since the button's "border" is really the `::before`(top+right)/`::after`(bottom+left) bevel pair, not a real CSS border, the fix swaps each pseudo-element to the *other one's* background-image/blend-mode on `:active` (top+right goes dark, bottom+left goes light), keeping each one's own `clip-path` so `.square` and non-square each still get their own inset/miter.

### Spell Line: a new filterable/surfaceable dimension, from migration 019's `spell_line` nodes
Three places: a tag-input filter on the Spell Finder (`#spellline-tag-wrap`), the same filter plus a passive badge on Class Browser's spell cards, and a line item in the Spell Finder's hover tooltip. All three read `spellLine`/`spellLineId`, attached to spell data server-side by `src/graph.ts`'s `withSpellLine()` (via the `member_of` edge index) — `getAllSpells`/`getSpellsForClass` attach it to every spell they return, and `rankZones()` attaches it per zone-ranking spell entry and accepts a `spellLineIds` filter param (`GET /api/plan?lines=...`).

**Filter semantics**: same as the existing multi-class "Shopping For" filter — an *additive* (union) facet layered onto whatever class/level narrowing already produced, not a per-tag AND (a spell belongs to at most one line, so requiring all selected lines to match would always be empty). Bypassed entirely when a specific spell is pinned, same reasoning as the class filter bypass: Specific Spells is an exclusive override.

**Class Browser's Spell Line field is conditionally hidden**: only shown when the Category select is on "Spells" *and* the current class selection's spells actually have line data (`rawSpells.some(s => s.spellLineId)`) — checked against the pre-line-filter set, not the already-filtered one, since checking the filtered set would be self-referential once a line is picked.

### Sidebar filter panel: shared by Spell Finder and Class Browser, both markup and CSS
Class Browser's filters moved from a horizontal `.filter-bar` into a left sidebar matching the Spell Finder's `.controls-panel` — a tag-wrap field growing wider as chips are added would otherwise reflow every field to its right in a horizontal bar; a sidebar's fields stack full-width instead, so a growing field only pushes its own row down.

Since both pages now need the identical layout (sticky 300px column at ≥1100px, fields flip from row to column at that width, label-above-input), the shared parts moved into `theme.css`'s "Sidebar filter panel" rule (`.controls-panel`/`.planner-controls`/`.field`/`.panel-actions` + the `@media (min-width: 1100px)` breakpoint) instead of being duplicated per page. Each page keeps only what's genuinely its own on top: Spell Finder's `.field .range-picker` sizing and its 3-column `order` values (sidebar/results/status-panel); Class Browser has neither.

Went one step further than CSS sharing: `public/components.js` gained a `SidebarPanel({ fields, actions })` component that builds the `.controls-panel > .planner-controls > .field* > .panel-actions` wrapper markup itself, and a `tagWrapHtml(prefix)` helper for the repeated tag-wrap chip-list-plus-search-input markup every `setupTagInput()` instance needs. Both pages' `renderSidebar()` now call `SidebarPanel(...)` and inject the result via `outerHTML` into a `<div id="controls-panel-slot">` placeholder, rather than hand-writing the wrapper HTML directly in each page. Each field's own control (a `<select>`, a tag-wrap, the range-picker) is still supplied as a raw HTML string — those vary too much across fields to usefully generalize further, unlike `MacroButton`/`setupTagInput` which fully own their markup.

**Desktop layout requires `#browser-content`/`#browser-results` to add zero left/top padding** — the sidebar's own right border is the shared seam against the first result's left border (the "console" look: adjoining panels share a border, not a gap), same as the Spell Finder's `.controls-panel`/`#results` split. An earlier pass added `padding-left: 14px` on `#browser-content` when first converting to the sidebar layout, which visibly broke that shared-border look; removed.

### Class Browser's category picker needed `classBadges()` to handle an empty selection
`classBadges(entryClasses, selected, levelLookup)` filters `entryClasses` down to just the ones in `selected` — correct when the tag box's whole purpose is showing per-class detail for a chosen class. But once "no classes selected" became the normal *browsing-everything* state (see "No classes selected means all classes" above), `selected` is legitimately `[]`, and `.filter(c => selected.includes(c))` on an empty array always returns nothing — so every spell/ability card silently lost its class badge entirely while browsing unfiltered. Fixed: when `selected.length === 0`, show every one of the entry's classes instead of filtering to none, matching the same "no filter = show everything" convention used everywhere else in this app.

### Spell Finder sidebar is grouped into four labeled sections: Faction, Spells, Level, Location
`.field-group-label` (theme.css) marks each group with a small caption above its first field, each group closed off by a `.control-sep` divider — the same ornamental divider that used to just sit once between the Race/Primary Class/Deity trio and everything else. Order was deliberately picked as Faction → Spells → Level → Location, moving the Levels range picker up from last position to its own group between Spells and Location, rather than leaving it trailing after Current Zone where it read as an afterthought.

Only the Faction group's label carries a `title` tooltip ("Race, Primary Class, and Deity only affect vendor faction standing — they don't filter which spells show up below") — that's the one dimension genuinely confusable with a spell filter (a plausible first guess is "picking a race narrows which spells I see"), so it needed an explanation, not just a name. Spells/Level/Location are self-explanatory groupings and don't need one. `.field-group-label[title]` is the only selector that gets `cursor: help`, so the other three don't visually promise an explanation they don't have.

**`.field-group-label`'s first version had the hierarchy backwards** — 10px, 0.75 opacity, no text-shadow, versus `.field label`'s 11px/full-opacity/shadowed — making the section headings the *least* legible text in the panel, reported back as "hard to read." Fixed by making it unambiguously the more prominent of the two: 13px, bold, `--parchment` colored, same text-shadow formula `.field label` uses for legibility against the marble turbulence texture. Computed exact contrast ratios before picking the color rather than guessing — `--gold` (3.65:1) and `--gold-bright` (4.37:1) both measure under this app's own 4.5:1 AA bar for small text against `--stone-1`, despite `--gold` reading fine elsewhere on this same marble (e.g. `.zone-route .route-sep`, which is much larger); `--parchment` (6.03:1) was the established stone-panel body-text color already comfortably clearing it.

### Owned-spell tracking shares one localStorage key across both pages
`getOwnedSpells()`/`setSpellOwned()`/`clearOwnedSpells()`/`OWNED_KEY` moved from `app.js` into `components.js` so the Spell Finder and Class Browser read/write the exact same `eq-planner-owned` set — marking a spell owned in one shows up in the other immediately (same origin, same localStorage). Class Browser's `renderSpellCard` adds a checkbox per spell card; deliberately no filtering/counting UI there (no "N owned" summary, no hide-owned toggle) — Class Browser is a browse/reference page, and duplicating the Spell Finder's status-panel machinery for a simple "mark it" checkbox would be scope the request didn't ask for.

**First version of the checkbox was a bare, unlabeled native checkbox placed first in the card header**, ahead of the spell name — reported back as unclear (no indication of what it does) and "very pronounced" (a stark native-chrome checkbox competing with the bold `h3` for first-glance attention, with no surrounding context like the Spell Finder's status panel to hint at its purpose). Fixed: added a visible "Owned" text label, moved it after the spell name with `margin-left: auto` (right-aligned, reads as a secondary control), shrunk it, and muted its default color (`--ink-muted`, brightening to `--gold` only on hover or when checked via `:has(input:checked)`) rather than sitting at full gold-accent brightness unconditionally. Scoped to `.spell-check-labeled` (not the shared `.spell-check` the Spell Finder's row checkbox already uses) since only the Class Browser instance was reported as a problem — the Spell Finder's checkbox sits in a different, already-established context (a compact `.spell-row` next to a small `.spell-chip`, with the status panel's owned-count reinforcing what it means) and wasn't touched.

### Whole-app light-source consistency pass: top-right everywhere
Every raised/inset surface across all three pages now shares one light source — top-right — instead of MacroButton/MacroSocket being a documented exception to a top-left convention used everywhere else (`.zone-card`, `.controls-panel`, `.field select`/`.tag-wrap`, `button`, `.spell-detail`, `.zone-badge`/`.hops-badge`, `.mana-bar`, plus the small circular "gem" specular highlights on `.spell-chip`, `.loading`, the range-slider thumb, and the zone-name LED dot). MacroButton/MacroSocket were left untouched — they were already correct; everything else got flipped to match them.

**The mechanical rule, derived once and applied everywhere**: for `border-color: top right bottom left`, swap the *right* and *left* values (top/bottom stay put) — a raised element's old `hi lo lo hi` (light top+left, dark bottom+right) becomes `hi hi lo lo` (light top+right, dark bottom+left); a sunken element's old `lo X X lo` becomes `lo lo X X`. For a `radial-gradient(circle at 35% 30%, ...)` sphere highlight, mirror the x-coordinate around 50% (35%→65%) so the highlight sits up-and-right of center instead of up-and-left.

**Inset `box-shadow` offsets needed an empirical check, not a guess** — CSS's inset-shadow offset-to-corner mapping isn't obvious from the property values alone, and guessing wrong would have silently shipped a bevel that contradicted its own `border-color`. Verified by rendering a plain test div with exaggerated offsets (`inset -20px -20px white, inset 20px 20px black`) and inspecting where each color actually lands: **positive `inset dx dy` paints that color on the top+left inner edge; negative paints it on bottom+right** (a diagonal pair). For the anti-diagonal pair this app actually needs (top-right/bottom-left), the offsets must have *opposite* signs: confirmed `inset -X +Y` → top+right, `inset +X -Y` → bottom+left. So a raised panel's old `inset 1px 1px white, inset -1px -1px black` (diagonal, matching its old top-left border) becomes `inset -1px 1px white, inset 1px -1px black` (anti-diagonal, matching the new top-right border) — negate the x-offset, keep the y-offset, on every directional inset shadow in the file. Shadows with a zero x-offset (e.g. `inset 0 3px 7px black`, or the mana-bar's internal seam/knob details) have no left-right asymmetry to begin with and were left alone.

Cross-checked the derived rule against `.macro-btn:active`'s existing (and, per this session's earlier fix, already-verified-correct) pressed-state shadow before trusting it on everything else — its `inset 2px -2px white, inset -2px 2px black` plugs into the same rule and correctly predicts white-bottom-left/black-top-right, matching its own code comment. Two independent confirmations (the standalone test render, and this cross-check) before touching 15+ call sites.

**One deliberate, documented exception**: `.mana-bar::after`'s per-bead specular gradient stays top-left, because it's reverse-engineered pixel-for-pixel from a zoomed capture of the real client's vitals bar (see the vitals-bar entries above) — matching the reference image takes priority over matching our own convention there, and a future pass shouldn't "fix" it back to top-right.
